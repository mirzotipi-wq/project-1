# Cassa — Master Engineering Plan

**Cassa is a point-of-sale operating system for 64-bit ARM retail hardware, written entirely in Zig.**
This document is the authoritative 100-phase delivery plan. Each phase is small enough to
review in one sitting, and each one ends with a written, testable exit criterion. Phases are
executed strictly in order; nothing is declared done because it compiles — it is done when the
exit criterion has been observed on QEMU or on real hardware and the evidence is recorded.

---

## 0. Mandate

| | |
|---|---|
| **Product** | Cassa POS OS — a dedicated till OS for shopping stores |
| **Architecture** | AArch64 (ARMv8.0-A baseline and newer) |
| **Language** | 100% Zig, kernel to pixels |
| **Boot** | UEFI stub on real hardware; QEMU `virt` ELF image for development |
| **Shape** | Monolithic kernel + isolated user-space services (POS, payments, printing, UI) |
| **Primary KPI** | A cashier can complete a sale, take payment, print a receipt, and close a shift — offline, on day one of a power cut, with zero data loss |

### 0.1 Non-negotiables

1. **Zig only.** Every line of executable logic — boot, kernel, drivers, filesystem, network,
   TLS, compositor, UI toolkit, and the POS application itself — is Zig source. There are no
   `.c`, `.S`, `.cpp`, Rust, Python or JavaScript files in the build. There is no libc.
2. **No borrowed kernels.** No Linux, no Zephyr, no seL4, no U-Boot. Cassa boots from firmware
   into its own entry point.
3. **Runs on any AArch64 CPU.** Compiled for the ARMv8.0-A baseline so that it runs on
   Cortex-A53/A55/A72/A76/A78/X-series, Neoverse, Apple silicon and Graviton. Hardware
   differences are discovered at boot through device tree and ACPI, never compiled in.
4. **POS-grade reliability.** No data loss on power failure, no half-committed sale, no
   unlabelled failure. Every subsystem has a defined degradation mode.
5. **Deterministic, reviewable security.** Capability-based isolation for every service,
   signed updates, encrypted storage, auditable privileged actions.

### 0.2 What "100% Zig" means precisely

| Artifact | Language | Rationale |
|---|---|---|
| Kernel, drivers, services, UI, apps | Zig | Mandate |
| Build system (`build.zig`) | Zig | Also emits the linker script |
| Linker script | Generated by Zig at build time | Keeps a second language out of the tree |
| Pad/entry stubs | Zig `naked` functions with Zig inline assembly | No separate `.S` files |
| Documentation | Markdown | Prose is not code |

The only external binaries involved in development are the Zig compiler and QEMU. Neither
ships inside the OS image.

### 0.3 Hardware support tiers

- **Tier 1 (must):** QEMU `virt` (CI), Cortex-A53/A72 boards, integrated POS terminals.
- **Tier 2 (should):** Raspberry Pi 4/5 class SBCs, NXP i.MX8, Rockchip RK3399.
- **Tier 3 (later):** Apple silicon VMs, Graviton bare metal, server-class Neoverse.

### 0.4 Targets

| Metric | Target |
|---|---|
| Cold boot → POS screen interactive | < 3.0 s |
| Tap → painted response | < 50 ms |
| Local checkout commit (scan → sale stored) | < 100 ms |
| Resident memory on 512 MB device | < 64 MB |

### 0.6 Verification strategy

1. **Host unit tests** (`zig build test`) for pure logic: allocators, codecs, tax maths,
   cart rules, font metrics, FDT/ELF parsers, protocol state machines.
2. **QEMU boot gate** (`zig build run`) — every commit must boot to a shell and pass the
   in-kernel self-test suite.
3. **Deterministic snapshot tests** for the UI toolkit (render to memory, compare hashes).
4. **Fault injection**: power-cut simulation, media errors, OOM, malformed frames.
5. **Hardware lab**: real POS terminal, receipt printer, scanner, card terminal.

## Stage A — Foundation: from reset vector to an observable kernel

### Phase 1 — Toolchain and reproducible build `[x]`
**Goal:** One command builds a bootable AArch64 image; no second language in the tree.
**Build:** `build.zig` with a freestanding target (ARMv8.0-A baseline, `+neon +fp`), a
linker script generated as a build artifact, `zig build run` for QEMU, `zig build test` for
host tests, warnings-as-errors, and a build manifest stamped with git describe.
**Done when:** `zig build` produces an ELF with a correct entry point, and a from-scratch
clone builds with no extra tooling or shell scripts.

### Phase 2 — Boot entry and handoff `[x]`
**Goal:** Take control of the CPU from firmware in a defined state.
**Build:** Naked `_start`: mask interrupts, set SP_EL1, capture the device-tree pointer,
clear BSS, detect current EL, park secondary cores, jump into `kmain`. UEFI path drops to
the same entry after `ExitBootServices`.
**Done when:** QEMU prints a boot line and the kernel stack/BSS are provably zeroed.

### Phase 3 — Early UART console `[x]`
**Goal:** Byte-accurate output before anything else exists.
**Build:** PL011 driver with FIFO handling, baud/word-length setup from the device tree,
polled TX/RX, and a `Writer` interface usable by the rest of the kernel.
**Done when:** Formatted output appears on QEMU's serial console at boot.

### Phase 4 — Kernel logging `[x]`
**Goal:** Structured, levelled, timestamped diagnostics.
**Build:** `klog` with compile-time max level, per-subsystem scopes, uptime stamps, a lock
for SMP safety, and an in-memory ring buffer that survives a panic for post-mortem dumping.
**Done when:** `klog.info`/`warn`/`err` render consistently, and the ring can be dumped.

### Phase 5 — Panic and fatal-error surface `[x]`
**Goal:** A crash is a diagnosis, not a mystery.
**Build:** Zig panic hook, `@panic`/`unreachable` capture, register dump (PC, LR, SP, ESR,
FAR), stack scan, boot-phase breadcrumb, and an explicit halt policy (watchdog reset in
production, hang in debug).
**Done when:** An intentional fault prints a labelled report instead of resetting silently.

### Phase 6 — Device tree discovery `[x]`
**Goal:** Learn the machine instead of hard-coding it.
**Build:** FDT parser (header validation, string block, node/property walk), memory node
extraction, `/chosen` bootargs/stdout-path, interrupt-controller and timer discovery.
**Done when:** Physical RAM size, UART base and GIC addresses are read from the tree and
logged, with QEMU varying `-m` sizes producing different reported totals.

### Phase 7 — Physical memory manager `[x]`
**Goal:** Hand out and reclaim physical pages safely.
**Build:** Bitmap allocator over usable RAM, reserved ranges for kernel/DTB/MMIO, single-page
and contiguous allocation, free counters by zone, and poison-on-free in debug builds.
**Done when:** Host tests cover alloc/free/coalesce accounting and QEMU reports the expected
page totals for several RAM sizes.

### Phase 8 — Kernel heap `[x]`
**Goal:** A real allocator behind `std.mem.Allocator`.
**Build:** Boundary-tag free-list allocator with splitting, coalescing, alignment support,
OOM propagation, usage accounting and debug poisoning.
**Done when:** Host tests pass a randomized alloc/free/coalesce workload with zero leaks and
no corruption, and the kernel can use `std.ArrayList`/`std.fmt.allocPrint`.

### Phase 9 — MMU and address-space discipline `[x]`
**Goal:** Caches on, W^X enforced, MMIO descriptors correct.
**Build:** 4 KiB granule page tables, MAIR/TCR setup, identity map during bring-up, normal
cacheable vs device-nGnRnE attributes, guard pages, permission API, TLB maintenance.
**Done when:** The kernel runs with MMU and caches enabled, unmapped accesses fault with a
decoded report, and a deliberate write to read-only text traps.

### Phase 10 — Exception vectors and fault taxonomy `[x]`
**Goal:** Every exception has an owner.
**Build:** 16-entry vector table (runtime-patched branch table, 2 KiB aligned), full trap
frame save/restore, ESR/ISS decoding for data/instruction aborts, SVC, alignment, and
SError, plus a fault handler that names the cause in plain language.
**Done when:** `svc`, a bad load, and an undefined instruction each produce a distinct,
accurate report instead of a hang.

## Stage B — Time, interrupts and concurrency (complete: 11-18, 20; 13 partial, 19 deferred)

### Phase 11 — Interrupt controller (GICv3 + GICv2 fallback) `[x]`
**Goal:** Route and acknowledge interrupts on both generations of GIC.
**Build:** Distributor/redistributor/CPU-interface init, priority and group configuration,
SPI/PPI enable, acknowledge/EOI, spurious handling, IRQ handler registry.
**Done when:** The timer interrupt fires and is acknowledged on QEMU (GICv3) and on a
GICv2 target without code changes.

### Phase 12 — Generic timer `[x]`
**Goal:** Monotonic time and periodic ticks.
**Build:** CNTFRQ calibration from the device tree, CNTPCT read, CNTP compare programming,
1 kHz tick, one-shot deadlines, `uptime`/`sleep`/`sleepUntil` primitives.
**Done when:** Uptime advances accurately, a 1-second busy-wait is within 1% of wall clock,
and ticks survive 10^6 interrupts without drift or lost interrupts.

### Phase 13 — Interrupt framework refinement `[~]`
**Goal:** Interrupt handlers cannot deadlock or stampede.
**Build:** Top-half/bottom-half split, IRQ-safe spinlocks, handler latency counters, storm
detection (disable a line that fires > N times per tick), and threaded IRQ support.
**Done when:** A deliberately storming line is throttled and logged, with the rest of the
system still responsive.
**Verified:** IRQ-safe spinlocks, per-CPU interrupt and tick counters, and the
spurious/unhandled tallies reported by `irq` (0 and 0 on a live boot) exist. Storm throttling
and threaded IRQs are not built yet: `logstorm` proves console serialisation, not IRQ storms.

### Phase 14 — Spinlocks and atomics `[x]`
**Goal:** Correct SMP primitives with deadlock detection.
**Build:** Ticket spinlock, IRQ-save/restore variants, exclusive/acquire-release helpers,
lock-order validation in debug builds, per-CPU state.
**Done when:** A contended counter test across 4 cores is exactly correct, and an intentional
ABBA lock order panics with both lock sites named.
**Verified:** `sync.zig` ships `SpinLock` (test-and-test-and-set with event hints),
`TicketLock`, `IrqSpinLock`, acquire/release atomics, and `WaitQueue`/`Semaphore` on top.
`stress 4 20000` on four cores reports 80000/80000 with 0 lost updates and no page drift.
Lock-order validation (the ABBA panic) is deferred to the Stage D deadlock detector, which
needs the lock graph the file server will introduce.

### Phase 15 — Kernel threads and context switching `[x]`
**Goal:** Multiple execution contexts inside the kernel.
**Build:** Thread struct, callee-saved context switch, per-thread stacks with guards, idle
thread, thread exit and reaping.
**Done when:** Two threads ping-pong a counter with correct interleaving and no stack bleed.
**Verified:** `thread.zig` (24 slots, 64 KiB stacks since phase 41, fabricated trap frames) plus
`sched.zig` (idle thread per core, exit and reaping). `threads` lists live contexts with
state, core, run count and stack; `preempt` shows three threads interleaving on one core;
`reap 8` and `reap 12` return every stack to the PMM (0 pages leaked). Guard pages are not
mapped yet.

### Phase 16 — Preemptive scheduler `[x]`
**Goal:** Fair, bounded-latency CPU sharing.
**Build:** Round-robin across priority classes, tick accounting, timeslice tuning, run-queue
per CPU with load balancing, scheduler statistics.
**Done when:** Three CPU-bound threads each get within 5% of their fair share, and an
interactive thread wakes with < 1 ms latency under load.
**Verified:** 1 kHz tick-driven preemption with 4-tick slices, per-CPU round-robin queues,
work stealing and pinning. `preempt 1000` pins three spinning threads (none of which ever
yield) to one core: 22..22 timeslices each, all three progressing — only possible through
preemption. Iteration spreads of 6-12% track hypervisor time stealing from the vCPU, not
scheduler bias; the slice counts themselves are equal.

### Phase 17 — Sleep, wait queues, synchronization `[x]`
**Goal:** Blocking without burning CPU.
**Build:** Wait queues, mutex/condvar/semaphore, sleeping mutexes, timeout-aware waits,
priority donation for lock holders.
**Done when:** A producer/consumer stress test with 4 threads passes 10^6 items with no lost
wakeups and no priority inversion beyond the donation bound.
**Verified:** `WaitQueue`, `Semaphore` (signed permit count, generic over its backend so the
identical code runs in host tests) and `sleepMs`/timed waits. The host suite covers blocking,
wakeup ordering and semaphore accounting. Priority donation waits for priority classes.

### Phase 18 — SMP bring-up `[x]`
**Goal:** Use every core in the terminal.
**Build:** PSCI `CPU_ON`, per-CPU stacks/trap frames/GIC init, IPI for reschedule and TLB
shootdown, boot barrier, per-CPU data accessor.
**Done when:** 4 cores report online, TLB shootdown is verified by a mapping test, and
`-smp 1/2/4/8` all boot cleanly.
**Verified:** PSCI `CPU_ON` with per-CPU stacks, trap frames, GIC CPU interface, timer and
TPIDR_EL1 state. `cores` reports 4/4 online with independent tick, switch, preempt and IRQ
counters on each, and `-smp 1` through `-smp 4` boot. TLB shootdown is implemented as an IPI
but has no user address space to shoot yet (phase 22).

### Phase 19 — Deferred work `[ ]`
**Goal:** Keep interrupt context tiny.
**Build:** Per-CPU workqueues, softirq classes, delayed work tied to the timer, cancellation.
**Done when:** Block-device completion is processed off the IRQ path, and a 10k-item
workqueue drains with bounded latency.
**Status:** deliberately deferred. Its done-when needs block devices (Stage D); softirqs
without a producer would be an unused abstraction.

### Phase 20 — Tracing and self-tests `[x]`
**Goal:** Observability that survives production.
**Build:** Boot self-test suite, per-subsystem counters, tracepoints with a ring buffer,
`kassa selftest` command, boot-time assertions.
**Done when:** Every boot runs the self-tests and reports a single pass/fail verdict.
**Verified:** every boot runs the self-test suite and prints one PASS/FAIL verdict per
probe; `cores`, `threads`, `irq`, `mem`, `time`, `stress`, `preempt`, `reap` and `logstorm`
expose live counters; the scheduler keeps a 64-entry switch ring that panic and fault reports
dump.

## Stage C — Privilege, processes and IPC (21-22 complete)

### Phase 21 — EL0 and syscalls `[x]`
**Goal:** Move code out of the kernel.
**Build:** EL0 transition, `svc` entry path, syscall table with argument validation,
`copy_from_user`/`copy_to_user` with range checks.
**Done when:** A user program prints via a syscall and cannot read kernel memory.
**Verified:** `user` runs the embedded program at EL0 and `uprobe` proves the
contract. The program prints through `write`, receives its pid and the uptime
from the kernel, yields and exits 0 (8 ms in a measured run). A `mrs tcr_el1`
is reported by the hardware as an undefined instruction at EL0 (EC 0x00,
ESR 0x2000000) at pc 0x80000268 — EL0 has no access to that register at all, so
the encoding is undefined there rather than "trapped"; a load from kernel
text 0x40080000 raises a level-3 permission fault; both are logged with the pid,
kill only that process, and the kernel keeps running. `write()` with kernel text
and with an unmapped address each return -14 after the kernel refuses to follow
the pointer (the `rejected_ptr` counter advances by 2 per run). EL0 passes the
call number in x8, and the kernel validates every pointer twice: against the
process's declared regions with their rights (`uaccess.check`, host-tested) and
against its live page tables (`mmu.translateFrom`). Not done yet: a separate
fault-tolerant `copy_from_user` (validation is followed by a direct copy) and
capability checks — phase 23 replaces the region list with a handle table.

### Phase 22 — Address spaces `[x]`
**Goal:** Isolated per-process memory.
**Build:** TTBR0 per process, ASIDs, map/unmap/protect, demand-zero anonymous memory,
user stack growth, guard regions.
**Done when:** Two processes at the same virtual address cannot see each other's data.
**Verified:** every process gets its own L0 (a copy of the kernel's), its own
clone of the kernel's L1, and its own L2/L3 pages, so the kernel and its devices
stay mapped while a process runs and no user-reachable mapping leaks in. A
context switch installs the matching root in TTBR0_EL1 and invalidates the TLB,
before the old thread is marked off-CPU (reaping frees those tables). Two
processes write different secrets to 0x81000010 — same virtual address, different
physical pages — and after 25 context switches each still reads its own value
(`uprobe` step 5). Teardown releases every frame and table: five launch/exit
cycles return the free-page counter exactly (128440 -> 128440). Not done yet:
ASIDs (a full TLB invalidate per switch is the honest cost), demand paging (all
frames are allocated at load), stack growth (a fixed four-page stack with an
unmapped guard below it) and an ELF loader — the demo is a flat blob embedded in
the kernel image.

### Phase 23 — Capabilities `[x]`
**Goal:** Authority is a first-class, transferable object.
**Build:** Capability slots, rights masks, derivation, revocation, per-process handle tables,
kernel object headers with refcounts.
**Done when:** A process without a capability cannot reach a device, and revocation cuts
access immediately.
**Verified:** every process owns a 16-slot handle table and a handle number is
`(generation << 8) | (slot + 1)`, so a closed or revoked slot can never be named again and
zero is never a valid handle. A handle carries a rights mask — READ 1, WRITE 2, EXEC-or-MAP 4,
CONTROL 8 — and the kernel resolves the handle before it looks at any user pointer: a forged
number returns EBADF (-9), never a fault and never another process's memory. Derivation needs
CONTROL on the parent plus a subset mask; revocation walks the parent chain, invalidates the
whole subtree and bumps generations, so later use fails with EBADF while the parent keeps
working. Objects are the console, a shared ledger (64-byte cell, version, epoch), the
supervisor (another process's state, exported read-only) and a page object holding one kernel
frame with magic `0xCA55A0B100000023`, which only a handle carrying EXEC-or-MAP can place in a
process at 0x81500000. Eight syscalls (20-27) are the whole surface: query, derive, revoke,
close, read, write, control, map. `caps` prints the object table with reference counts.

The probe passes on `-smp 4` and `-smp 1` with identical numbers. The first process is born
with handles 1/2/3/4 and passes all six cases: granted rights work (case 1); mapping a ledger
without EXEC and controlling a read-only supervisor both return EPERM -1 (case 2); slot 10,
slot 200 and handle 0 all return EBADF -9 without faulting (case 3); a derived CONTROL handle
works, is revoked, and is then EBADF while its parent still answers (case 4); two live
processes (pids 111 and 112) hold the same ledger and the read-only one gets EPERM for write
while its read succeeds (case 5); deriving until the table is full returns EMFILE -24 and
closing one handle lets the next derive succeed (case 6). Both holders exit 0. The run
recorded 28 capability calls, 310 user syscalls, 13 spawned processes, 2 caught faults, and
the ledger ends at version 4, epoch 2, 14 references, with derivations 28, revocations 2,
refusals 7 and 2 live tables.

### Phase 24 — IPC endpoints `[x]`
**Goal:** Fast, typed message passing between services.
**Build:** Endpoint pairs, synchronous call/reply, 64-byte inline payloads plus handle
transfer, deadlines, backpressure.
**Done when:** A call/reply round trip sustains > 100k messages/s on QEMU, and a blocked
receiver never spins.
**Acceptance (concrete):**
1. An endpoint is a kernel object of kind `endpoint`; `ipc_create` returns a handle carrying
   `rwc`, and any handle with `w` may send or reply, `r` may receive, `c` may hand the
   endpoint to another process.
2. A message is exactly 64 bytes carried inline (`tag` plus seven words); the kernel copies it
   into the receiver's own buffer while the receiver's address space is loaded, so no message
   ever depends on another process's raw pointer.
3. `ipc_call` blocks the caller until the server replies; the reply lands in the caller's
   buffer and the reply length is the return value.
4. One handle may travel with a message. Transferring needs `c` on the handle (EPERM
   otherwise); a never-allocated or closed number is refused with EBADF before anything is
   published, so a refused call delivers no message; the receiver gets a fresh handle in its
   own table whose mask is the sender's minus `c`.
5. Revocation crosses processes: revoking the sender's handle after a transfer makes the
   receiver's installed copy fail with EBADF on its next use.
6. Deadlines: a call that is not answered within its timeout returns -ETIMEDOUT (110), leaves
   no stale request behind, and the channel still works afterwards; a reply that arrives after
   the caller gave up is refused with -EAGAIN (11).
7. Backpressure: an endpoint holds at most one request and one reply; a second sender blocks
   until the slot frees or its deadline expires.
8. A process that was never granted the endpoint gets EBADF for a number it does not hold and
   EINVAL for a handle that is not an endpoint, survives both, and exits 0.
9. A blocked receiver never spins: its thread state is `blocked` and its run counter does not
   advance while it waits.
10. A call/reply round trip sustains > 100,000 messages/s (two messages per round trip) on
    QEMU with four cores, measured over at least 300 round trips.
11. No regressions: phases 1-23 keep passing, host tests stay green, and the probe passes on
    `-smp 1` and `-smp 4`.

**Verified:** endpoints are capability objects (`cap.Kind.endpoint`) and five syscalls
(28-32) are their whole surface: `ipc_create`, `ipc_send`, `ipc_call`, `ipc_recv`,
`ipc_reply`. A message is exactly 64 bytes (`tag` plus seven words) copied by the kernel
into the receiving process's own buffer while that process's address space is loaded, so no
message ever depends on another process's pointer. `ipc_call` publishes a request, parks the
caller (`blocked` plus an absolute deadline) and resumes it when the answer is published;
`ipc_recv` parks a receiver until a request arrives, and a sender that finds a parked
receiver copies the message straight into it - one context switch instead of a poll. An
endpoint holds at most one request and one reply, so a second sender parks until the slot
frees or its deadline expires: that is the whole backpressure story.

One handle may travel with a message. Transferring needs `c` on the handle (EPERM
otherwise); a never-allocated or closed number is refused with EBADF *before* anything is
published, so a refused call delivers no message; the receiver's copy carries the sender's
mask minus `c`, and its parent link points into the sender's table. That last detail is new:
`revoke` now walks every table, so revoking the sender's handle kills the receiver's copy
immediately (a phase-23 gap closed here). A reply that arrives after the caller gave up is
refused with EAGAIN rather than handed to the next call.

The probe (`uprobe` step 10) passes on `-smp 4` and `-smp 1`. Server (mode 6) and client
(mode 5) are born holding the bootstrap endpoint; the server creates an endpoint and
transfers it to the client over that channel, so even the channel the client calls through
arrives as a handle. Client cases: 11 handoff received as a transferred handle; 12 call and
reply; 13 a READ+CONTROL ledger handle travels, the receiver reads through it and gets EPERM
for write; 14 a never-allocated number (0xDEAD) refused with EBADF; 15 a closed number
refused with EBADF; 16 the sender revokes its handle after the transfer and the receiver's
copy is EBADF; 17 a 10 ms deadline returns ETIMEDOUT (-110) against a server that answers
after 30 ms; 18 the channel still works and the server reports its late reply was refused
with EAGAIN (-11); 19 2000 round trips, all exact; 20 a clean shutdown. Server cases: 21
endpoint created; 22 handoff transferred; 23 exactly one transfer request reached it (the
forged ones never left the client) and the transferred handle read once; 24 the abandoned
reply was refused. Outsider (mode 7, never granted the endpoint): 31 EBADF for a number it
never held, EINVAL for a ledger handle, EPERM for a page handle; 34 bootstrap handle 0. All
three processes exit 0.

### Phase 25 — Shared memory and notifications `[x]`
**Goal:** Bulk data without copying.
**Build:** Shared memory objects, mapping into multiple address spaces, futex-style wait and
wake, event counters.
**Done when:** Two processes exchange a 4 MiB buffer with zero copies and correct wakeups.
**Acceptance (concrete):**
1. A shared-memory object is a capability object of kind `shm` holding up to 1024 kernel
   frames (4 MiB). `shm_create` returns a handle carrying `rwc`; the frames are zeroed when
   the object is created, so a peer can never read another object's old data.
2. `shm_map` maps the object into the caller's address space at a kernel-chosen base inside
   the user window and returns that base. Mapping needs `r`; the mapping is writable only if
   the handle also carries `w`, so one object can be read-write in one process and read-only
   in another.
3. Two processes map the same object: a word written by one is read by the other at the same
   offset with no copy in between (the kernel only installs page tables), and the 4 MiB buffer
   survives a full pattern pass in both directions.
4. `shm_unmap` removes this process's mapping, clears the page-table entries, drops the region
   and flushes the TLB; a second unmap of the same object is refused with EINVAL, and a later
   `shm_map` succeeds again at a free base.
5. Futex-style notification: `shm_wait(handle, offset, expected, timeout)` sleeps only if the
   32-bit word at `offset` still equals `expected` (EAGAIN -11 if it changed), returns 0 when
   woken, and ETIMEDOUT (-110) when the deadline passes. `shm_wake(handle, offset, count)`
   wakes up to `count` waiters and returns how many it woke; each wake bumps the object's
   event counter, which the shell prints.
6. Rights are enforced on the handle, never on a user pointer: a handle without `r` cannot
   map or wait (EPERM -1), a handle without `w` cannot wake (EPERM), a non-shm handle is
   EINVAL, and a forged or out-of-range handle is EBADF (-9) with no fault.
7. A process that was never granted the object cannot reach it: it has no handle (EBADF) and
   no mapping in its address space, and it survives every refusal and exits 0.
8. No regressions: phases 1-24 keep passing, host tests stay green, and the probe passes on
   `-smp 1` and `-smp 4`.

**Verified:** a shared-memory object is a capability of kind `shm` holding up to 1024 zeroed
kernel frames (4 MiB) from one 2048-page pool, created by `shm_create` (33) which returns a
handle carrying `rwc`. `shm_map` (34) installs those frames in the caller's page tables and
returns the base: the mapping is writable only when the handle carries `w`, so one object can
be read-write in one process and read-only in another without a flag from the user. Nothing
is copied — the kernel only writes page-table entries, so a word stored by one process is the
word the other reads. `shm_unmap` (35) clears the translations, drops the region and flushes
the TLB; a second unmap is EINVAL and a later map succeeds again at the same slot.

`shm_wait` (36) is futex-shaped: it sleeps only if the 32-bit word at `offset` still equals
the expected value, returns EAGAIN (-11) if it already changed, 0 when woken, ETIMEDOUT
(-110) on its deadline; `shm_wake` (37) releases up to `count` sleepers, returns how many it
released and bumps the object's event counter. Everything is decided under the object lock,
so a wake that lands between the value check and the park cannot be lost.

### Phase 26 — Processes and ELF loading `[x]`
**Goal:** Run separately built programs.
**Build:** ELF64/AArch64 loader (segments, permissions, BSS), argv/envp, process lifecycle,
exit status propagation.
**Done when:** The POS shell launches a user-space binary by name.

> Scope note: the standalone VFS phases come later in this plan, so the name lookup runs
> against a read-only image store (a table of embedded files) rather than a filesystem. The
> loader consumes real file bytes and the shell launches by name, which is the observable
> contract this phase owns; the store is the one call that a VFS will replace.

**Acceptance (concrete):**
1. A program built by the same toolchain as its own ELF64 executable — separate segments,
   separate data, separate BSS — is embedded as *file bytes*, not a flat blob, and the kernel
   parses it at runtime.
2. The parser validates ELF64/little-endian/ET_EXEC/EM_AARCH64, refuses a bad magic number,
   a wrong word size, a wrong machine, a truncated header or program table, a segment whose
   file bytes do not fit in the file, `p_filesz > p_memsz`, a segment outside the user
   window, overlapping segments, a writable-and-executable segment, and an entry point
   outside an executable segment — before a single page is allocated.
3. The loader maps each page once with the union of the permissions of the segments that
   touch it, refuses a page that would end up both writable and executable, copies the
   file-backed part of each page and leaves the rest zero, so BSS arrives as zeroes.
4. The startup ABI is x0 = argc, x1 = argv, x2 = envp, with the strings and both pointer
   vectors built on the user stack before the thread is admitted; SP is 16-byte aligned.
5. `exec <image> [args...]` in the shell loads the image by name, runs it, and prints its exit
   status; a missing image is refused as "no such image" and nothing is spawned.
6. `images` lists the store and `elf` prints the last load plan (entry, segments, bytes, BSS)
   and the load/refusal counters.
7. No regressions: phases 1-25 keep passing, host tests stay green (with new host tests for

**Verified:** `pos.elf` is a genuinely separate program: `zig build` compiles it as its own
executable from `src/user/pos.zig` (its own linker script puts .text, .rodata, .data and .bss

runtime. It is 67 KB of file for 1366 bytes of loadable content — the padding is the linker's
64 KiB segment alignment, and the loader honours it because it maps pages, not offsets.

(r-x at 0x80000000, r-- at 0x80001000, rw- at 0x80002000), 1366 file bytes, 1622 memory

segments touching it and refuses any page that would be writable *and* executable; that rule
is why the program's linker script aligns permission groups to pages, and why a hand-made

### Phase 27 — Lifecycle and fault isolation `[x]`
**Goal:** One crashing service cannot take the till down.
**Build:** Supervisor per service, restart policy with backoff, crash loop detection,
core-dump-to-storage, orphan reaping.
**Done when:** Killing the printer service in a loop leaves checkout functional.

> Scope note (tightened): "core-dump-to-storage" is a **crash record** — pid, fault kind,
> fault address, pc, esr, the eight argument registers and eight words of the faulting user
> stack — captured while the process still owns its address space, kept in a small kernel ring
> and printed by `dumps`. The VFS phases own files; this record is the part of a core file a
> supervisor can act on, and every field is measured, not inferred from a log line.

**Acceptance (concrete):**
1. `service start|kill|stop <name>` manages a named service; bare `service` lists name, state,
   pid, restarts, failures and policy for every slot, plus the global counters.
2. A service that dies is restarted by the supervisor with exponential backoff
   (5, 10, 20, 40, 80, 160 ms, capped at 160), and the delay the policy chose is recorded on
   the service record, so the ladder is observable from outside.
3. Consecutive failures are counted. At the policy's limit the service is parked `failed`
   (crash loop detected) instead of being restarted forever; a run that stays up for the
   policy's stability window resets the count.
4. A faulting program leaves a crash record (`dumps` shows pid, cause, pc, esr, registers and
   stack words) and cannot take the machine down: the shell and every other service keep
   running.
5. Stopping a service kills its child and reaps it. Live process count, address-space count
   and the page allocator return to their pre-service values (orphan reaping), and a killed
   child that blocked in a syscall still dies.
6. Checkout keeps working while the printer service is killed in a loop.
7. No regressions: phases 1-26 keep passing, host tests stay green (new host tests for the
   restart policy), and the probe passes on `-smp 1` and `-smp 4`.

**Verified.** The supervisor is a kernel thread of its own (`svc`) that polls the service table
every 10 ms and never blocks on a child. Each entry is a name, an image, argv, and a pure
`restart.Policy` (max_restarts 6, base 5 ms, cap 160 ms, stable window 250 ms). The policy
itself is `src/kernel/restart.zig`, free of kernel dependencies, so backoff, the crash-loop
decision and the stability reset are unit-tested on the host (3 new tests, 55/55 total).

Read that transcript for what it is: the printer was killed **seven** times; the supervisor
brought it back six times with 5/10/20/40/80/160 ms between attempts (its own `svc` log lines

and register/stack words, and cost no live process, address space or page: after `stop`, live
processes and spaces are back to 0 and `reaps` counts every child the supervisor buried.

**A scheduler defect this phase found and fixed.** The supervisor is a thread that blocks and
wakes ~100 times per second, which is far more than anything before it, and it exposed a
use-after-free in the context switch: `reschedule` cleared the outgoing thread's `on_cpu`
flag *before* returning the incoming frame, i.e. while the core was still executing on the
outgoing thread's stack. Another core's tick could then reap that thread and free its stack
in that window; the symptom was an occasional `eret` into data (a fault report whose ELR was
ASCII from a log line) or a resumed frame with a nonsense `spsr`. Four-core idle boots with the
unpinned supervisor died within ~17 s; pinned, they survived, which is what pointed at
migration rather than at the supervisor's logic. The fix moves the hand-off into the exception
trampoline: `reschedule` records `pc.switching_out`, the trampoline calls `cassa_after_switch`
immediately after `mov sp, x0`, and only there is `on_cpu` cleared. A wake that arrived during
that window is deferred (`pending_wake`) and must be applied at that same point or it is lost —
the first version of the fix omitted that and hung the shared-memory step, which the probe
caught at once. The frame validation also checks the saved PSTATE mode now, so a corrupt frame
is reported with the thread's name instead of jumping into whatever address it names.

Measured evidence for the fix: with the unpinned supervisor, two 36 s four-core idle boots and
four consecutive four-core probe boots ran with zero faults and `RESULT: PASS`; before the fix
the same idle boot faulted every time within ~17 s. `-smp 1` passes too.

Host tests: 55/55 (3 new: backoff doubles and caps, the crash loop trips at max_restarts and not

`stress 4 20000` -> 0 lost; `preempt 1000` -> PASS (`22..23` slices); `reap 8` -> 0 pages
leaked; `logstorm 4` -> 96/96 intact; `cores` -> 4 cores online; `irq` -> 0 spurious, 0
unhandled; `-m 1024M` -> 1024 MiB, 259456 pages free; `textwrite` -> permission fault at

supervisor load made the server occasionally answer the abandoned call after the client had
already moved on. No assertion was changed — the window only gives the server time to finish,
which is what the test always assumed.

**Gap (open):** the service table is four static slots with the image name compiled in, and the
policy is per-service but not persisted, so a `failed` service stays parked until someone
restarts it by name — that is the service registry and manifest work of phase 28. The crash
record ring holds four records in kernel memory and is lost on reboot (no filesystem yet); it
captures registers and eight stack words, not the full stack or the faulting page. Supervision
is polling, not event-driven: a death is noticed within one 10 ms tick, and a restart can
therefore be up to one tick later than the policy's delay. Orphan reaping covers children of
supervised services; a process spawned directly by the shell is reaped by the shell's `wait`
as before, and there is no process group or parent/child tree yet. The scheduler's
`cassa_after_switch` hand-off has survived the soak above, but it is the kind of change that
deserves a longer stress run than one phase can give it; `stress 4 20000` and the four-core
probe boots are the evidence so far.

### Phase 28 — Service registry `[x]`
**Goal:** Services find each other without hard-coded handles.
**Build:** Namespace tree, path-based lookup, service manifests, lazy start, health probes.
**Done when:** The POS app resolves `pos://printer` at runtime and degrades gracefully when
it is absent.

> Scope note (tightened): the "namespace tree" is a **flat table of opaque names**, not a
> directory hierarchy, and "service manifests" are the name, image, argv and restart policy a
> slot already carries, registered under a name — there is no manifest language yet. What is
> built is the part the POS app needs: a kernel-owned name-to-identity table, a by-name lookup
> that answers with a reason, lazy start, and a supervised service whose absence is a value
> rather than a fault. Health *probing* is the supervisor's existing liveness check (a service
> whose child died is restarted or parked) surfaced through the lookup reason; there is no
> separate request/response health protocol.

**Acceptance (concrete):**
1. `registry` lists every registered name, its service slot, state, generation and the global
   counters; `pos://` names are validated by one pure function (`registry schema: 1-16 chars,
   `[a-z0-9-]`, no leading or trailing `-`, scheme required).
2. Re-registering a live name, registering an unknown target, and registering when the table is
   full are each refused with a distinct reason, and no entry changes.
3. `resolve <name>` returns a reason: ok, unknown name, not running, crash-loop parked, exited.
   The reason is a stable numeric code the ABI fixes, written to a user process unchanged.
4. `ensure <name>` starts a registered but stopped service and returns its pid (lazy start), and
   a lookup that finds a service mid-restart answers `restarting` instead of failing.
5. A POS program calls the syscall and exits with the reason code, so degradation is provable at
   the call site: live service -> 0, parked crash loop -> 4, unknown name -> 1.
6. The table is fixed-size (8 entries) and re-registration is idempotent for a dead name; nothing
   in the lookup path allocates, so the registry cannot grow with load.
7. No regressions: phases 1-27 keep passing, host tests stay green (new host tests for the name
   rules and the reason mapping), and the probe passes on `-smp 1` and `-smp 4`.

**Verified.** The name rules and the reason mapping are `src/kernel/names.zig`, free of kernel
dependencies: `validate`, the `Reason` enum with ABI-fixed values 0..9, `reasonFor(lifecycle,
child_alive)` and `reasonLabel`, covered by 5 host tests. The table is `src/kernel/registry.zig`:
8 entries of name + service slot, an `IrqSpinLock`, and `register`, `lookup`, `ensure`, `count`,
`entryAt`. Every registration is checked against the slot's live state, so a name cannot point at
a slot that does not exist; duplicates are refused, not overwritten. Lookup reads the service
record and its generation under the registry lock, which is the same lock the supervisor takes
when it changes a state, so a lookup can never interleave with a restart half-applied: it sees
either the old generation running or the new one restarting, and says which. `service.Service`
gained a `generation` counter bumped by `launch`, which is what makes "same service, new
incarnation" observable from user space. User space reaches all of it through one new syscall,
`UserNr.resolve = 38`: `resolve(name_ptr, name_len, out_pid)` returns the reason code and writes
the pid only on ok, with the pointer range validated like every other string argument.
`pos.elf resolve <name>` prints the outcome and **exits with the reason code**, which is how the
probe proves graceful degradation rather than describing it. The shell gained `registry`,
`resolve <name>` and `ensure <name>`.

**Scheduler follow-up (after phase 28): run-queue lifecycle.** The kill-path churn of step [13]
exposed an intermittent four-core panic, `selected thread 0 in state unused`, and the phase-28
notes recorded it as open. It is now fixed. The panic was a **queue entry naming a thread that had
already been reaped and whose slot had been recycled**: `thread.destroy` zeroes a slot, so a queue
still holding that slot pops "thread 0 in state unused" — and because `destroy` also clears the
freed thread's own `next`, the queue's *predecessor* is left pointing at the zeroed slot, which is
how a boot that had run for seconds suddenly selected a thread id of 0.

The cause was a **duplicate run-queue entry**, not a stolen one. There were two publish sites for
the same outgoing thread: `reschedule` pushed it when it was runnable, and `cassa_after_switch`
pushed it *again* if a wake arrived in the window between them (`on_cpu` was still true, so
`makeReadyLocked` recorded `pending_wake` instead of queueing). The thread then had two entries.
One was consumed when it ran; the survivor could be popped after the thread had blocked, died and
been reaped, i.e. after its slot was zeroed. The earlier "queued while on_cpu" reading was a
symptom: the `double_run_events` counter that appeared to confirm it was actually counting the
core's own **idle** thread, which is legitimately on-CPU whenever a core falls back to it, so that
counter said nothing about real duplicate entries at all.

What changed, and the invariant it establishes:

* **Invariant R:** every run-queue entry names a thread that is `ready` and that no core is
  executing; every `ready` thread is in exactly one run queue. The transition into `ready` and the
  push happen together under the scheduler lock at exactly two sites — `makeReadyLocked` for a
  parked (off-CPU) thread, and `cassa_after_switch` for the thread that has just left the core.
  `reschedule` no longer queues the outgoing thread at all; it only decides what the thread will
  be (ready/blocked/dead) and folds a deferred wake into that decision. Publishing happens in the
  trampoline, at the first instant the stack is genuinely free, in the same critical section that
  clears `on_cpu`.
* `pushTail` asserts Invariant R and counts a refusal (`queue_violations`); the reaper refuses to
  free a thread that is still referenced by any run queue (`deferred_reaps`); a stale queue entry
  is dropped instead of resumed; and the tick audits for a `ready` thread that has sat in no queue
  for more than 50 ms, reports it with the site that made it ready, and re-queues it (`stray_ready`)
  so a lost wake becomes one late slice and a number instead of a stalled service.
* The idle fallback is no longer judged by the queue-entry rules, which is what the old
  `double_run_events` count was really measuring.
* Nothing allocates on the switch path; the only added state is three diagnostic words per thread
  (`ready_site`, `ready_ms`) and three counters. `-smp 1` boot and the switch soaks are unchanged.

**Deadline enforcement in IPC, and the two probe races it exposed (fixed).** After the run-queue
repair, roughly one four-core boot in ten still failed EL0 IPC cases 17/18/24 while the same boot's
2000-round-trip throughput test passed. It was not a wake-latency regression: `ipc.reply` refused a
late answer only when the caller was no longer parked **and** its deadline had passed. If the answer
arrived while the caller was still parked (it had not run its own timeout path yet), or after
`sweep` had cleared the caller and zeroed the deadline, the kernel accepted the answer for a caller
that was about to return ETIMEDOUT. That one race produced all three symptoms at once: the call
returned a reply instead of a timeout (17), the endpoint kept a stale answer that the same thread's
next call then took as its own (18), and the server's late reply was accepted rather than refused
with EAGAIN (24). The fix is in `ipc.reply`: a deadline that has passed refuses the answer, decided
by the deadline alone and independent of which thread runs first, and `sweep` no longer erases the
deadline when it clears a parked caller. That is the contract the comment in `call` already stated —
the server may answer after the caller has given up, and that answer must be refused. It is a
kernel fix, not a probe constant: no assertion changed and no window was widened for it.

Two probe observations were also *sampled* rather than *waited for*, which is what the remaining
5-10% of boots were hitting: step [13] read the crash-loop state immediately after the last kill
(catching the previous restart's transition) and step [14] tried to observe a 5 ms backoff window
from a thread that is itself scheduled on four cores. Both now wait, with bounded timeouts, for the
exact state they assert; step [14] also sets the 100 ms backoff it observes (a policy input, not
the property under test) and restores it. Nothing was weakened: every assertion is unchanged and
the state still has to be reached.

**Deferred:** names are flat, not a tree, and there is no per-name ACL, so any process can resolve
any registered name (phase 30's capability manifests are where that belongs). The registry does

persisted manifest store needs the filesystem phases. `pos://` is the only scheme, and it is

bound for the life of the boot (the table is fixed and the probe registers two). Health is
liveness-as-a-reason, not a request/response probe: a service that is running but wedged answers
ok. The pid a lookup returns can be stale by the time the caller uses it — it is an identity at
resolution time, and the generation counter is what lets a caller notice the service was replaced.

### Phase 29 — Resource accounting `[x]`
**Goal:** No single service can starve the till.
**Build:** Per-process memory/CPU/handle quotas, OOM scoring, memory pressure notifications,
watchdog escalation ladder.
**Done when:** A leaking service is capped and reported while checkout stays responsive.

**Shipped.** `quota.zig` is the policy as pure arithmetic over three counters — pages, handles and
CPU milliseconds in a rolling window — with the 80 % "near" band, an OOM score weighted 600/250/150
towards memory, and a three-rung ladder (`warn` → `throttle` → `kill`) driven by strikes. It is
host-tested: levels at the boundary, a zero quota, score ordering, the ladder, and saturation when a
runaway reports absurd numbers.

`account.zig` is the ledger and the watchdog. Every EL0 process gets an entry at creation (`attach`
from `process.spawnWith`/`spawnElf`), a service's quota is attached *before* its thread is admitted
(`spawnElfQuota`) so its very first instruction already runs under it, a restart cannot escape it,
and the entry is dropped when the process slot is reused. Enforcement sits at the three funnels
where a resource is actually handed out, not in a periodic scan:

  * **Frames** — `AddressSpace.page_budget` is set from the quota; `allocFrameInto` and `mapShared`
    refuse past it and count the refusal. Shared pages are charged to the process that maps them.
  * **Handles** — `cap.allocateSlot` asks the ledger before installing a slot, so a leak of authority
    is bounded exactly like a leak of memory (`cap.quota_refusals`).
  * **CPU** — the scheduler charges `cpu_ms` at each switch and will not pick a thread whose
    `throttled_until_ms` is in the future. A throttled thread stays `ready` and keeps its single
    queue entry — invariant R is untouched — it simply gets no CPU for one window.

One kernel watchdog thread samples every 100 ms and never blocks on a process it watches, so a
spinning service cannot delay the accounting meant to catch it. Memory pressure is a real comparison
of free pages against a watermark with a critical mark below it: the highest-scoring process is
named, every live entry records the pressure, and past the critical mark a process well over its
quota is killed. `SYS_ACCOUNT` lets a process ask about *itself* — usage, level, score, pressure
flag — which is the notification a service can act on; `accounting` prints the same table from the
shell.

Two probe facts are stated rather than hidden. The harness image (`spawnWith`) gets a permissive
ledger: it exists to exercise every capability and to saturate cores on purpose, so it is accounted
for but not constrained — phase 29's limits are for services. And the `leak` program finds its
CONTROL handle by asking the kernel instead of assuming a slot order, then derives until refused.

**Measured (final build).** Step [15] prints on every probe boot:
`pressure: 127271 pages free, watermark 127272 -> 1 event(s), 0 victims  OK`,
`leaker: 1 handle refusal(s), 3 page-quota breach(es), then parked by policy  OK`,
`watchdog: warn 1, throttle 1, kill 1 (quota 8 pages, 6 handles, 40 ms/500 ms)` and
`till: 3/3 checkouts served while the leaker was capped  OK`. On the same build: 20/20 consecutive
four-core probe boots `RESULT: PASS` with zero panics, zero hangs and
`0 double-run, 0 queue violation(s), 0 stray ready`; 5/5 single-core boots; `killoop 150` twice at
150/150 with zero anomalies; `stress 4 20000` 0 lost updates; `preempt 1000` PASS; `reap 8` 0 pages
leaked; 65/65 host tests. The preemption soak also pins its three workers to one explicitly chosen

the "single core" check flaky on a busier machine.

The IPC probe needed one more kernel fix to stay deterministic under the new load: an answer is now
tied to the *call* it belongs to by a request sequence (`req_seq`/`recv_seq`/`rep_seq`), so a late
reply that crosses a newer call is never delivered as that call's answer, and the caller is woken
only for the answer to the call it is waiting on. Deadline refusal stays as the second line of
defence.

**Deferred:** quotas are per-process, not per service group, and there is no runtime UI to change
one (the service record's `quota` is the knob). CPU accounting is wall-clock scheduled milliseconds,
not a hard real-time reservation. Pressure is reported and scored but there is no reclaim — pages
return only when their owner dies, and the shared-memory pool is still monotonic (`shm.create` never
gives pages back), which is why the leak probe exercises its cap through authority. `SYS_ACCOUNT` is
a poll, not a push: no process is interrupted by a notification.

### Phase 30 — Sandbox policy `[x]`
**Goal:** Least privilege by construction.
**Build:** Declarative per-service syscall and capability manifests, W^X enforcement, no
ambient authority, policy validation at build time.
**Done when:** A deliberately compromised renderer cannot open a raw block device.

**Shipped.** `sandbox.zig` holds the policy as data: a `Manifest` is a name, the capabilities a
process is born with, and a 64-bit mask of the system calls it may make. Four are shipped —
`harness` (everything, for the test image), `service` (a POS service: console, ledger, supervisor,
page, IPC and shared memory), `storage` (console, page, **block**) and `renderer` (a console and the
right to ask about itself, nothing else). `validate` rejects a duplicate id or name, an empty
capability list, a duplicate capability kind, a right bit that does not exist, an empty right mask,
a capability kind that cannot be granted at birth (endpoints and shared memory are minted by their
users), a syscall bit that names nothing, a page declared writable **and** executable, a block
object outside the storage manifest, and a renderer that holds anything but its console. It is
called from a `comptime` block, so a policy mistake fails `zig build` — the check runs on the
machine that compiles, not on the till.

Authority is now granted from the manifest and nowhere else. `cap.Kind.block` is a real object
created at boot whose first sector carries a signature and the sector size; `cap.grantSpecs` grants
exactly the capabilities a manifest lists, in declaration order, and `process.spawnElfInner` uses it
for every ELF launch (the demo harness keeps its four fixed handles, which the `harness` manifest
mirrors). A service's `manifest` sits next to its `quota`, so a supervisor restart cannot escape
either one.

Enforcement has three independent layers, and the probe measures them separately:

  * **The gate** — `syscall.handleUser` checks `sandbox.allowsForPid` before dispatch, not inside
    each call. A refusal is `E_PERM`, bumps a global counter and a per-process counter, and is
    logged only for the first four refusals of a process so a compromised program cannot turn a
    denial into a console flood.
  * **The object** — `SYS_BLOCK` (40) reads eight bytes at a byte offset from a `block` handle and
    requires `R_READ` on an object whose kind really is `block`. A process whose mask *does* name
    the call but which holds no such capability is refused here, and every failed attempt is
    counted (`sandbox.block_denials`).
  * **The mapping funnel** — `mmu.wxAllowed` refuses a writable-executable page, `addrspace.mapPage`
    asks it before building a descriptor and counts the refusal (`mmu.wx_refusals`), and the
    manifest validator refuses a policy that would ask for one. The ELF loader already refuses a
    segment that is both writable and executable.

`sandbox` prints the manifests and the counters from the shell; probe step [16] is the acceptance
test.

**Measured (final build).** Step [16] prints on every probe boot:
`manifests: 4 validated at build time, renderer caps 1 (console only)  OK`,
`storage: sector 0 signature through its block handle  OK`,
`no-block: 16 calls allowed by the mask, refused by capability  OK`,
`renderer: 16 handle probes + 1 undeclared call refused by the mask  OK`,
`block: 18 denial(s) recorded, 0 reads without the object  OK`,
`W^X: writable-executable mapping refused at the funnel (1 total)  OK`. The storage service reads
`0xB10CCA55A0B10030` from the device and exits 0; the compromised renderer tries every handle 1..16
for the raw device, tries to create shared memory it never declared, and exits 0 only if all 17
attempts were refused and it still holds exactly one handle. Two of the eighteen denials are the
storage service probing console and page before it finds its own block handle — the scan is part of
the program, and it is counted like any other refused attempt.

**Deferred (open items).** Manifests are compile-time data: changing a service's policy is a
rebuild, and there is no signed-manifest store or runtime policy editor (the `sandbox` command is
read-only). Masks are per-sandbox, not per-service-instance, so two services sharing `service` share
one table entry; per-instance manifests need the policy store above. The block object is a 64-byte
in-memory sector rather than a virtio-blk device — `SYS_BLOCK` is the ABI that driver will keep, and
the entitlement question will not change when the bytes become real. A transferred block handle is
not re-checked against the receiver's manifest (transfer moves an existing capability, and the
receiver's mask still gates the call), there is no revocation sweep that kills a live holder, and
denials are counted and logged to the console but never written to an audit log on disk. W^X covers
every user mapping but there is no guard-page policy around them yet.

## Stage D — Devices, DMA and human interface hardware

### Phase 31 — Driver model `[x]`
**Goal:** Probe order that is data-driven, not hand-ordered.
**Build:** Device objects, driver registration with compatible-string matching, dependency
ordering, init error isolation, hotplug notifications.
**Done when:** Disabling a device in QEMU removes its driver cleanly with a clear log.

**Shipped.** Boot order used to *be* the policy: `kmain` called `gic.init`, then `timer.init`,
then whatever came next, because that is what the QEMU `virt` machine happens to need. Nothing
checked that the hardware was present, nothing could say "the timer needs the interrupt controller
first", and a driver that could not start had no way to fail except by taking the machine down.
`driver.zig` replaces that with a model:

  * **Devices are data.** `discover` walks the device tree once and turns every node with a
    `compatible` property into a `Device`: node name, compatible strings in tree order, `reg`
    regions and `clock-frequency`. Nothing in the model knows a device by name.
  * **Drivers claim compatible strings.** A device binds to the first driver whose claim list
    contains one of the device's strings, testing the device's list first, so the most specific
    string wins. Five drivers ship: `console` (pl011), `gic` (GICv2 and v3), `timer` (the generic
    timer, both the v8 and v7 compatible strings), `rtc` (PL031) and a deliberate
    always-failing `selftest-fail` that exists only to prove failure isolation.
  * **Dependencies are declared.** `timer` names `gic`; the model orders drivers topologically
    (Kahn, deterministic tie-break) and refuses a cycle instead of probing it.
  * **Failure is isolated.** A probe returns an error, the device is marked `failed` with the
    reason, a listener is told, and boot continues. A device whose dependency did not bind is
    `skipped`, never half-initialised.
  * **Devices come and go.** Removing a device unbinds its dependents first, calls the driver's
    `remove` hook, then notifies listeners; adding it back probes it again. A driver without a
    `remove` hook is boot-critical and the model refuses to unbind it.
  * **The tree is the probe order.** `0 bound, N waiting` plus an `idle: '<driver>'` line per
    driver with no device makes "the machine does not have it" visible and distinct from "it
    broke".

The console is still installed by the firmware handoff before any driver can log, and the pl011
driver adopts it from the tree; if no timer binds, boot halts with a reason instead of running a
scheduler without ticks.

`devices` prints the device table, bindings and hotplug counters; probe step [17] is the
acceptance test. Phase 31 also carries a real PL031 wall clock (`pl031.zig`) with host-tested
civil-date arithmetic — the first driver that exists for the till rather than for the kernel:
receipts need a date that survives a power cut, not uptime.

Two bugs came out of the acceptance work and were fixed at the source rather than worked around:

  * **`fdt.nextSibling` stopped at an `FDT_NOP` token.** A tree edited in place — which is exactly

  * **The IPC throughput gate and two call deadlines measured the host, not the kernel.** Case 19
    required an absolute 2000 msg/s, which the same code measured at 2346 msg/s on an idle boot and
    925 msg/s with other emulators running — with zero lost messages. It now compares against a
    same-boot baseline (a zero-length sleep takes the same two context switches) and keeps
    `good == rounds` as the correctness gate. Separately, calls that exist to prove *an answer
    arrives* were timing out on a starved guest (a vCPU can lose seconds under TCG on a shared
    host), so their tolerance is 10 s; the 10 ms deadline-refusal test is untouched. The probe also
    names the step that failed now, and the endpoint counts refused late replies, because
    "RESULT: FAIL" with no step is not a diagnosis.

On the final build: clean `rm -rf .zig-cache zig-out && zig build` with 0 errors and 0 warnings;

hangs; 5/5 single-core boots; `killoop 150` twice at 150/150 with 0 pages leaked; `stress 4 20000`
exact; `preempt 1000` PASS on a single core; `reap 8` 0 pages leaked.

**Deferred (open items).** Hotplug is a model-level operation plus a QEMU-level device tree without
the device; `virt` has no live hot-unplug without ACPI/PCIe hotplug, so the notification path is
exercised by removal in the running machine rather than by a physical unplug. There is no driver
unload beyond calling the remove hook, and no reference counting for a device another driver is
still using. Dependencies are declared between drivers, not between individual devices, which is
enough for a SoC but not for two instances of one bus. The 32 virtio-mmio slots and the PCIe host
bridge stay unbound until phases 32 and 33, and the GPIO controller has no driver yet (no button,
no cash-drawer line). The RTC is read-only: no alarm interrupt, no timezone or drift handling, and
the kernel has no `settime` path yet. Devices are not exported to userspace as `/dev` nodes.

### Phase 32 — PCIe host bridge `[x]`
**Goal:** Enumerate the terminal's internal buses.
**Build:** ECAM config access, bus/device/function walk, BAR sizing and mapping, MSI/MSI-X
allocation, legacy INTx fallback.
**Done when:** `lspci`-equivalent output matches QEMU's device list, including BAR layout.

**Shipped.** The terminal's internal bus is now a first-class device in the phase-31 model:
`pci-host` claims `pci-host-ecam-generic`, and every function it finds enters the device table as
its own object (`pci0:01.0`, compatible `pci,1b36:0005`, vendor/device/class, BARs, interrupt
capability). Nothing is hidden inside the bridge driver: the functions are unbound, appear in
`devices`, and are counted with everything else — which is what the virtio transport binds next.

What `src/kernel/pci.zig` does, driven entirely by the tree and the PCI register layout:

  * **ECAM access.** `ecamAddress` is the spec's bus/device/function shift into the 256 MiB
    window; config space is read and written as aligned 32-bit accesses only, with half-word and
    byte fields rebuilt inside their word.
  * **The root complex from the device tree.** `ranges` (decoded without being told the parent's
    address-cell width: every plausible width is tried, and ambiguity is refused rather than
    guessed), `bus-range`, `interrupt-map`/`-mask`, and `#address-cells`/`#size-cells`.
  * **Walk.** All 256 buses, 32 devices, 8 functions where the header says multifunction; every
    present function becomes a `Function` and then a device object.
  * **BARs.** Each BAR is sized by writing all ones and reading the mask back (restoring the
    original), decoded as 32-bit, 64-bit or I/O, assigned inside the host bridge's windows,
    written to the device, and read back to prove it took the address.
  * **Interrupts.** MSI (message registers in config space), MSI-X (table entry in a BAR) and
    legacy INTx through the tree's `interrupt-map`, in that order. The GICv2m frame is the MSI
    controller: its `SETSPI_NSR` register is the message address and the allocated SPI is the
    data. Every path is verified by readback — the MSI/MSI-X enable bit, the table entry, and the
    GIC's own ISENABLER bit for INTx — before a function is reported as connected.

**MSI unavailable, INTx fallback.** `tools/nop-node.zig` removes the `v2m@8020000` frame from a
QEMU-dumped tree, so the same image boots a machine with no MSI controller:
`irq: 1 connected (0 msi, 1 fell back to intx), msi unavailable (no GICv2m frame, no ITS): INTx
only  OK`, the virtio function routed to its SPI, and step [18] passes. INTx is not "declared":
`interrupt-map` resolves the pin to a controller line, the line is enabled, and the GIC's
ISENABLER bit is read back to prove it.

**Two real bugs the verification found, both fixed at the source:**

  * **An unassigned 32-bit memory BAR reads back zero, exactly like an absent one.** The first
    implementation treated `raw == 0` as "no BAR" and found nothing to place on a machine with no
    firmware. Only the all-ones write distinguishes them, so sizing always probes the mask now.
    (A second, related one: complementing a 32-bit mask in 64 bits made every size
    `0xffffffff00001000` and unmappable.)
  * **`interrupt-map`'s parent cell is a type and an *index*, not an interrupt id.** Map entry
    `SPI 3` means GIC interrupt 35. The kernel was enabling interrupt 3 — an SGI — which looks
    like a working route until the first interrupt arrives. The translation (`32 + n` for SPI,
    `16 + n` for PPI) is host-tested now.

### Phase 33 — Virtio transport `[x]`
**Goal:** One transport for block, net, input and GPU.
**Build:** Split virtqueue implementation, descriptor chains, feature negotiation,
interrupt coalescing, error recovery and queue reset.
**Done when:** A virtqueue echo test passes 10^5 requests under memory pressure.

**Shipped.** `src/kernel/virtio.zig` is the single transport every virtio class will share, and
`src/devices/virtio_mmio.zig` is the driver that binds the machine's 32 `virtio,mmio` transports to
it through the phase-31 device model. Each transport is a device object: claimed by compatible
string, listed in `devices`, counted with everything else, and a new `virtio` command prints the
table. The PCIe functions phase 32 publishes stay unbound by name.

What the transport is:

  * **Modern virtio-mmio (version 2) only.** Magic/version/device-id/vendor-id, the status
    ladder ACK → DRIVER → FEATURES_OK → DRIVER_OK, four 32-bit queue address halves and
    `queue_ready`. A version-1 (legacy) transport is refused by name and counted, never half-driven.
  * **Feature negotiation.** Both device feature words are read and the driver accepts
    `VIRTIO_F_VERSION_1` alone, then verifies the device kept FEATURES_OK. A feature this kernel
    does not understand is left off, never accepted blindly.
  * **Split virtqueues.** 64 descriptors, available ring and used ring in kernel memory — identity
    mapped, so the addresses written into the transport are the addresses the device reads and
    writes. Descriptor chains come off a free list and go back onto it; the available index is
    published exactly once, behind a barrier (`dsb sy` on the target, an atomic on the host tests).
  * **Completion draining and coalescing.** `drain` takes every completion the used ring holds, so
    one interrupt — or one poll — empties it, and any drain that returns more than one element
    counts as a coalesced batch. The interrupt status/ack registers are driven by `takeInterrupt`.
  * **Queue reset and recovery.** A request with no completion is detected by a bounded wait; the
    transport is reset (`queue_ready` 0, status 0), the ring rebuilt, and the request retried once.
    A second failure is reported as a failure, not hidden.
  * **A real device, end to end.** The entropy device takes a writable buffer through a split queue
    and the driver reads back the 64 bytes the device wrote: the first virtio request this kernel
    completes on hardware rather than on a model of one.

The echo self-test drives the same ring code from a software device that answers correctly, while
the page allocator is held down and churned. Step [19] on every probe boot:

`[19] virtio: negotiation, split queues, echo under pressure, recovery`
`transports: 32 slot(s), 1 with a device, 31 empty  OK`
`negotiate: version 2, VIRTIO_F_VERSION_1 acked by 1 device(s)  OK`
`queue: 1 live split queue(s), descriptor/available/used rings  OK`
`echo: 100000 request(s), 0 error(s), 25000 coalesced drain(s), 127175 page(s) before, 127175 after  OK`
`pressure: 8192 page(s) held (32768 KiB), 782 churn cycle(s), 0 allocation failure(s)  OK`
`recovery: 1 reset(s), timeout detected, retry completed  OK`
`served: 1 device(s) answered real requests; block/net/input/gpu protocols are later phases  OK`

32 MiB of pages are held for the whole run and one allocate/free cycle runs per 32 batches; the
free-page count is identical before and after, and fewer than 8192 held pages fails the step. The
machine's own accounting noticed the pressure without being told: `memory pressure: 127175 pages
free (< 127176) -> 1 event(s), 0 victims`.

The boot line matters: QEMU's virtio-mmio defaults to the **legacy** transport. The matrix boots
with `-global virtio-mmio.force-legacy=false -device virtio-rng-device`; without the flag every
transport is refused with `legacy or unknown transport version ... not driven` and [19] fails
loudly. That absence is detected and logged, never worked around.

**Four real bugs the verification found, all fixed at the source:**

  * **An empty transport was treated as a device that rejected the feature set.** Negotiation ran
    before the device id was inspected, so 31 empty slots reported `FeaturesRejected` and were
    marked failed. An empty slot is a transport with no device: it is now returned untouched and
    reported as empty.
  * **The available index was published twice.** The volatile store and the struct increment
    addressed the same word, so the device saw a gap, skipped the request, and the first real
    entropy request timed out twice. One writer, one increment. The echo device had the same
    mistake on the used ring; both now go through a single completion helper.
  * **The churn leaked the page it replaced** (3125 pages over one run), and the first pressure
    scale-up put 64 KiB of page addresses on the shell's stack — the scheduler caught it as
    `corrupt thread frame ... thread 7 'wd'`. The pressure array is static now and the free-page
    count is asserted, so a leak fails the step instead of passing quietly.
  * **A pre-existing IPC race, surfaced by the extra boot-time work:** a late reply to an abandoned
    call was judged against the endpoint's *current* deadline, which the next call had already
    replaced. The caller was protected by the call sequence, but the server was told its answer had
    been delivered, so cases 18 and 24 failed in two probe boots. The deadline of the call being
    answered is now recorded with its sequence when the request is taken
    (`recv_call_deadline`), and lateness is judged against that.

On the final build: clean `rm -rf .zig-cache zig-out && zig build` with 0 errors and 0 warnings;
86/86 host tests (four new: chain allocation/release, chain flags, used-ring wrap and batch size,
feature negotiation); 20/20 four-core probe boots `RESULT: PASS`; 5/5 single-core probe boots;
`killoop 150` twice at 150/150 with 0 pages leaked; `stress 4 20000` exact; `reap 8` with 0 pages
leaked; `preempt 1000` PASS on one core; zero panics and zero hangs.

**Deferred (open items).** There is no virtio-pci transport, so the virtio function phase 32 finds
on the bus stays unclaimed — modern virtio-over-PCI needs its own capability walk. There are no
device-class drivers: block, net, input and GPU protocols are phases 34, 37 and 38, so "one
transport for block, net, input and GPU" is the transport's design and not yet four working device
classes; only entropy is exercised end to end. Split rings only: no packed rings, no indirect
descriptors, no event suppression (the driver always notifies and drains by polling), one queue per
device (queue 0), and the queue size is 64 clamped to the device's maximum. The virtio-mmio
interrupt line is not routed to the GIC yet, so no virtio interrupt is taken: the coalescing rule
and ISR acknowledgement exist and are counted, but the completions in this phase are polled. The
echo device is software inside the kernel — it exercises the driver side of the ring protocol, not
a second piece of hardware. One pre-existing service-manager race is still open: `stop: live
processes 0 -> 1` failed once (a stop racing a supervisor restart tick); it has not recurred since
the IPC fix and is recorded here rather than papered over.

### Phase 34 — Block layer `[x]`
**Goal:** Reliable storage I/O with ordering guarantees.
**Build:** Virtio-block driver, request scheduler (simple elevator), flush/FUA handling,
retry with backoff, I/O statistics.
**Done when:** 10k random writes plus a flush survive an immediate QEMU quit with no
corruption reported by fsck.

**Shipped.** `src/kernel/block.zig` is the storage boundary and `src/devices/virtio_blk.zig` is the
first class driver on the phase-33 transport, registered through the phase-31 device model as a
block-class device. A `blk` shell command drives the same code path by hand.

What the block layer is:

  * **A backend seam, not a filesystem.** `block.Backend` is the interface a filesystem will be
    written against in phase 35: a batch of requests (read or write, an LBA, a sector buffer, an
    optional barrier), plus `flush` and the statistics block. Request and completion are separate
    values, so a caller can see what the driver did to each request.
  * **A simple elevator.** Requests are collected into a 64-request window, then stably sorted by
    starting LBA inside each read run and each write run, so a scattered batch becomes ascending
    runs the disk can serve without seeking backwards. Every reordered request is counted. A flush
    is a strict barrier: everything ahead of it is dispatched first, the flush is issued alone, and
    nothing behind it can jump the barrier.
  * **The virtio-blk protocol, for real.** Each request is a three-descriptor chain: a 16-byte
    header (type, reserved, sector), the data buffer, and a 1-byte status. Capacity comes from the
    device's config space at offset 0x100; `VIRTIO_BLK_F_FLUSH` (bit 9) is negotiated and the driver
    refuses to claim flush support if the device does not offer it. The device status byte is
    checked for every request and every failure is returned to the caller as a typed error
    (`NoSpace`, `IoError`, `Unsupported`, `BadStatus`) rather than logged and dropped.
  * **Retry with backoff.** A request the device never completes is bounded by a device timeout; on
    expiry the transport is reset, re-negotiated and the queue re-set up, and the request is
    retried. Three attempts, then failure. The counters (timeouts, retries, resets) are visible, so
    a silent retry cannot hide a broken device.
  * **Interrupts, with polling kept.** The virtio-mmio line for the disk is read from the device
    tree's `interrupts` property (SPI 13 + slot → intid 78 here) and registered with the GIC. The
    handler acknowledges the transport's interrupt status and counts it; the used ring is still
    drained by the request's caller, because the completion it is waiting for is on that thread's
    stack. Polling remains the fallback and is what the ring drain uses.
  * **I/O statistics.** Requests, sectors, errors, timeouts, retries, resets, flushes, elevator
    batches and reordered requests per device, printed by step [20] and by `blk`.

**The durability test.** The self-test writes a marker sector at LBA 0 and 10 000 data sectors at
distinct LBAs (8..10008) in a shuffled order — a real permutation, so "random writes" means 10 000
different places, not the same sector 10 000 times. It then flushes, reads all 10 000 back,
compares every byte and folds them into an FNV-1a digest, and finally writes the marker: a second
generation record carrying the seed, the sector count and that digest. **The marker is written only
after the data flush completed**, so its presence is itself proof the ordering held. The next boot
finds the marker, recomputes the digest from the disk and compares — that is the corruption check.

There is no filesystem in this kernel yet, so there is no `fsck` to run. Rather than claim one, the
check above is what this layer can prove: a byte-exact digest of everything written, verified on the
next boot after an unclean quit, with the marker gated behind the flush. A real `fsck` arrives with
the filesystem that can have corrupt metadata; the block layer's own evidence is stronger at this
level, not weaker.

    the next chains were malformed and every retry failed with `virtio-blk: missing headers`. Reset

  * **The injected fault was counted as an I/O error.** The forced timeout is deliberate, so the

    new process killed and the service left stopped.

    and space counts to a baseline taken up to ninety seconds earlier, so a service that
    legitimately exited during the step made the gate fail (`live processes 1 -> 0`). The property

    with 3–5 phantom mismatches on every boot while the digest of the same bytes matched the
    generated digest exactly; a diagnostic printed the first differing byte as 512 — i.e. there was
    none. Every sector comparison in the driver is now an explicit byte loop (`sameSector`), the
    verification no longer depends on the library call, and the digest independently confirms it.

**Deferred (open items).** The queue is depth one: one request in flight, dispatched synchronously
and waited on, so there is no request overlap and no benefit yet from the elevator beyond
reordering — queue depth and multiple outstanding requests are phase 35+ work. Flush is supported
but there is no separate FUA path (no `VIRTIO_BLK_F_FLUSH`-independent per-request FUA bit is set)
and the write-cache configuration (`VIRTIO_BLK_F_CONFIG_WCE`) is not touched. Discard, write-zeroes
and the read-only feature bit are not implemented. One virtio queue (queue 0), no MSI-X for virtio
(the disk is driven over virtio-mmio; virtio-over-PCI is still unclaimed from phase 33), and the
interrupt handler acknowledges the ISR but does not drain the ring itself. Hot-unplug of the disk
while requests are in flight is not exercised; detach is only at teardown. No filesystem, partition
table or `fsck` yet — `src/kernel/block.zig` is the seam those phases build on, and the durability
evidence above is the block layer's own.

### Phase 35 — Partition tables `[x]`
**Goal:** Find our data on any disk layout.
**Build:** GPT primary/backup parsing with CRC validation, MBR compatibility, partition
iteration, protective-MBR handling.
**Done when:** Images produced by the installer, `sgdisk` and Windows all enumerate correctly.

**Shipped.** `src/kernel/partition.zig` sits directly on the phase-34 block layer and answers the
question above the sectors: which ranges belong to a partition, and which writer produced the table.
A `part` shell command prints the attached disk's table, and probe step **[21]** exercises the
parser against real device I/O, including the negative cases.

What it does:

  * **GPT.** The header at LBA 1 and the backup at the last LBA are both read. Each is validated by
    its own CRC32 (the header's CRC field zeroed for the computation) and by the CRC32 of the
    partition entry array it names; the header is also checked against the LBA it was read from
    (`my_lba`), so a header cannot be believed in the wrong place. The primary is authoritative. If
    it is damaged the backup is read and the result is marked `backup_used` — the two copies are
    never mixed. A sound primary with a damaged backup still enumerates, and reports
    `backup_ok == false` instead of pretending.
  * **Entry iteration.** Type GUID, unique GUID, first/last LBA (inclusive, as the format stores
    them), attributes and the 36-unit UTF-16LE name are decoded; non-ASCII becomes `?` because a
    POS screen needs printable text. Entries with a zero type, inverted bounds or LBAs past the end
    of the disk are counted in `skipped`, never returned as valid partitions.
  * **MBR.** The four 16-byte entries at offset 446, including the bootable flag and the type byte.
    An extended container (0x05/0x0F/0x85) is followed through its EBR chain: each EBR's first entry
    is a logical partition relative to that EBR, its second entry links to the next EBR relative to
    the extended partition's start. The chain is bounded at 32 EBRs and rejects a repeat, so a
    corrupt table returns an error instead of spinning the kernel.
  * **Protective MBR.** The 0xEE entry every GPT disk carries is recognised and handed to the GPT
    parser. A protective MBR with no readable GPT (both copies bad) is reported as a refusal, not
    enumerated as one giant partition.
  * **A formatter for the fixture.** `writeGpt` writes a protective MBR, the primary entry array and
    header, the backup entry array and header, in an order a crash cannot make inconsistent (entries
    and the backup before the primary header, with flushes between) and computes all three CRCs.
    The installer does not exist yet — it is a later phase — so this is the installer-side primitive
    and the probe's fixture, not a user-facing `mkfs`.

first slice started 8 mod 16** — sizes 16 through 4096, independent of the data. `SCTLR_EL1.A` is
clear (the MMU enables alignment checking off), so this is not an alignment fault, and the host build
returns true for the same comparisons. `std.mem.eql`'s byte path (`eqlBytes`) scans 16-byte chunks
through a NEON vector and reduces the per-byte inequality with `@reduce(.Or, ...)`; on this
aarch64-freestanding build that path answers false for a byte-identical, 16-byte-misaligned first
argument. The diagnostic was removed; the kernel's verification comparisons stay explicit byte loops,
and the host test suite compares with `std.testing.expectEqual` on data where the host implementation
is correct.

**Deferred (open items).** The parser refuses an entry array larger than 16 KiB or more than 128
entries (the standard 128 × 128 layout is fine; 256-byte entries are not), and returns at most 16
partitions with the rest counted in `skipped`. A hybrid MBR's non-0xEE entries are not merged with
the GPT: the GPT wins and the MBR copies are ignored. The extended container itself is not listed as
a partition (its logicals are), and there is no repair path: a damaged primary is read from the
backup, but the primary is not rewritten. Nothing consumes the tables yet — no offset view for a
partition, no filesystem, no mount, no `fsck`; those are later phases. The writer exists for the
fixture and as the installer primitive, not as a user command, and there is no hotplug re-read of a
table when a disk is replaced. Integration was verified against GNU parted; `sgdisk` and Windows
images were named by the plan but are not available in this environment, and the record says so
rather than claiming them.

### Phase 36 — FAT32 on a partition view `[x]`
**Goal:** Consume the partition tables with a real filesystem, not just a parser.
**Build:** an offset block view that maps a partition's first/last LBA onto the disk with the phase-34
byte/sector bounds discipline; a pure-Zig FAT32 driver (BPB validation, FAT arithmetic, directory walk,
read, create, grow, delete, both FAT copies, FSInfo tolerance, every structure bounds-checked); probe
step [22] and a `fat` shell command; verification from both sides with a foreign formatter.
**Done when:** a FAT32 partition is mounted through the view, a file is read, created, written and
deleted by the kernel, and the same image is verified on the host with real FAT tools.

**Shipped.** `src/kernel/block_view.zig` and `src/kernel/fat32.zig` sit between the phase-34 block
layer and the shell. The plan's own phase-36 entry ("interrupt-driven console") was superseded by this
scope at the project owner's direction; it is carried as an explicit open item below rather than
silently renumbered or dropped, and phases 37+ keep their numbers.

What it does:

  * **Partition view.** `View` wraps the installed backend with `base_lba` and `sectors`, translating
    every request and checking it with `block.fits` before the disk sees it: a request past the
    partition's last sector, a zero-length or non-sector-multiple request, and a partition whose
    bounds lie outside the disk are all typed errors. A filesystem bug becomes `NoSpace`, never a
    write into the neighbouring partition. Tested on a recording backend for translation, the last
    sector, one past it, misaligned lengths, and a backend error passed through unchanged.
  * **Mount.** The BPB is validated field by field: sector size (512..4096, a multiple of 512),
    power-of-two sectors per cluster within the 32 KiB buffer, reserved and FAT counts, 32-bit FAT
    with a zero 16-bit field, total sectors within the view, data region arithmetic, root cluster in
    range, and a FAT large enough for its own cluster count. FSInfo is a hint: a bad signature, an
    unreadable sector or an impossible free count is ignored, the FAT stays authoritative. A volume
    whose first FAT entry is not a media marker is refused.
  * **FAT.** 28-bit entries, cached one sector at a time, written to *both* copies. Chain walks are
    bounded by the cluster count and reject entries outside the data region; a self-loop is detected
    while reading (the reader keeps the clusters it has seen and requires the chain to end exactly
    where the directory's size says it does).
  * **Directories.** 32-byte entries, 8.3 short names compared case-insensitively, LFN chunks decoded
    for display (a file another OS named "LongFileName.txt" enumerates and is looked up by its long
    name; the host test builds that entry by hand and reads it back). Creating writes an 8.3 short
    name and validates it *before* anything is allocated, so a rejected name cannot leave an orphan.
  * **Files.** Read by chain into a caller buffer; create, overwrite (the old entry is unpublished
    and flushed, then its chain freed, then the new entry is written into the same slot), grow across
    clusters, delete (entry first, then the chain, then the free counter). Write ordering is data →
    flush → FAT chain → directory entry → flush: a crash can reach the disk as a consistent file or
    as an allocated chain no directory entry references (an orphan that `fsck` reclaims), never as a
    live file pointing at clusters the FAT calls free.
  * **Allocation and counters.** First fit from a rotating hint, both FATs kept identical, FSInfo's
    free count and next-free hints rewritten after every create and delete.
  * **`check()`.** At-rest invariants, used by [22], by `fat check` and by the tests: no loops, no
    orphans, every file's chain exactly as long as its size requires, every allocated entry either
    free, EOC, marked bad or inside the data region, and the FSInfo counter equal to the FAT.
  * **Formatter.** `mkfs` writes a spec FAT32 (reserved 32, two FATs, FSInfo and backup boot sector,
    root cluster 2, zeroed FATs and root cluster, all three signatures) for the probe's scratch
    volume and as the installer-side primitive. It refuses a volume below FAT32's own 65 525-cluster
    minimum instead of producing a FAT16-shaped volume with a FAT32 BPB.
  * **Shell.** `fat info | ls | cat <name> | put <name> <text> | rm <name> | check` mounts partition 1
    of the attached disk through the view on first use and operates on that partition only.

**Bugs found and fixed in this phase.**

  * **The first [22] run panicked the kernel** (`scheduler: corrupt thread frame`, thread 7 'wd',
    `spsr=0x1`). Root cause: the fixture put two 4 KiB buffers on the shell thread's 32 KiB stack and
    the overflow overwrote a neighbouring thread's saved trap frame — the same class as the phase-35
    shell-stack bug. Both buffers are static now, with a comment saying why, and the probe is back to
    127031 free pages before and after.
  * **The scheduler's kernel-text window was a hardcoded constant** (`0x40080000..0x401b0000`).
    Phase 36's static buffers moved `.text` to `..0x401ab000`, within 16 KiB of that guess; one more
    phase of growth would have made every legitimate kernel frame look corrupt. The bounds now come
    from the linker (`symbols.textRange()`), so they cannot go stale. (No host test: the symbols only
    exist in the kernel image; the probe boots are the check.)
  * **`readFile` did not detect a loop that happened to fit the file's size.** A self-looping chain
    could satisfy a 2450-byte read by reading the same cluster five times and returning success. The
    reader now rejects a repeated cluster and requires the chain to end exactly after the last cluster
    the size needs; [22]'s corruption step and the host test both assert `error.Corrupt`.
  * **`writeFile` validated the 8.3 name after allocating clusters**, so `writeFile("a-rather-long-name")`
    returned `NameTooLong` but left an orphan chain behind (the next `check` caught it). Validation
    moved ahead of every write; the "8.3 name" host test now ends with a clean `check()`.
  * **A stray `cmdLspci()` sat in the `fat` dispatch branch** (left over from the phase-35 edit), so
    every `fat` command printed the PCI table after its answer. Removed; a boot with `part` and
    `fat ls` shows only those answers.
  * The formatter's FAT zeroing asked for 16 sectors through an 8-sector buffer; the first host test
    run caught the out-of-bounds index and it was cut to the buffer's size.

**Open items for phase 37 (not started).**

  * **The deferred console phase.** The plan's original phase-36 work — RX interrupt ring buffer, line
    discipline (echo, backspace, Ctrl-C), UTF-8 decode, flow control — is still to be scheduled
    explicitly; the shell today is the phase-12/20 line reader. Phase 37's framebuffer work is the
    next numbered phase as written.
  * **Long names on create.** LFN entries are decoded but not written, so a kernel-created file needs
    an 8.3 name; creating subdirectories and deleting them recursively is not implemented, and
    `check`/traversal handle the root directory only (subdirectories are counted, not descended).
  * **Crash window.** A crash between the FAT flush and the directory-entry flush can allocate a chain
    no entry references. `check` counts such orphans and `fsck.fat` reclaims them, but the kernel has
    no repair path and no journal; a POS deployment would want either.
  * **Limits.** Filesystem reads/writes are capped at 64 KiB (a static shell buffer), clusters at
    32 KiB, `check` at 1 048 576 clusters, and `mkdir`/FAT12/FAT16/exFAT, defragmentation, FSInfo

    timestamps (the driver stamps a fixed 2026-01-01) are all absent. The formatter writes the
    primary BPB and FSInfo, not every reserved-sector backup.
  * **Integration.** The installer does not call `mkfs` yet, the `fat` command always takes partition
    1 (no selection or subdirectory paths), and a replaced disk is not re-read or re-mounted. The
    phase-35 `part` command and this `fat` command are separate readers of the same table; a mount
    API shared with a future VFS is the natural next step.

### Phase 37 — Framebuffer `[x]`
**Goal:** Pixels on the panel.
**Build:** Bochs-display driver first (simple linear framebuffer), virtio-GPU second, HDMI
modesetting later; EDID parsing, double buffering, panic-to-screen handoff.
**Done when:** A test pattern renders at the panel's native resolution and panics are visible
on screen, not just serial.

**Shipped.** The first pixels are on a panel, and the path from a PCI function to a legible panic is
complete end to end. Five pieces:

  * **EDID (`src/lib/edid.zig`).** Base-block parser: header, manufacturer/product/serial, week/year,
    physical size, eight standard timings, four 18-byte descriptors (detailed timing or display
    descriptor), range limits, extension count and checksum. A detailed timing decodes
    hactive/hblank/vactive/vblank, sync offsets and widths, polarity and interlacing, and reports a
    refresh computed from the pixel clock rather than assumed. Errors are typed (`TooShort`,
    `BadHeader`, `BadChecksum`, `NoTimings`), and a panel with only standard timings still yields a
    usable mode.
  * **Framebuffer core (`src/kernel/fb.zig`).** One pixel path for everything: rectangles with
    clipping, gradients, `x8r8g8b8`/`r8g8b8`/`r5g6b5` formats, strided rows, bitmap text with
    scaling and centring, the self-test pattern, the boot splash and the panic screen. Every write is
    bounds-checked and allocation-free, so the same code is safe from a fault handler with no heap.
    `verifyReadback()` writes a known colour, reads it back through the MMU and restores the original
    pixel: proof that the mapping is the memory the device scans out.
  * **Font (`src/lib/font5x7.zig`).** Printable ASCII as 95 hand-authored 5x7 row-major glyphs
    (readable Zig literals, not an opaque blob), one blank column of advance, a fallback for anything
    outside ASCII, and tests that the table is exactly 95 glyphs, that no glyph overflows five
    columns, and that text metrics exclude the trailing column.
  * **Bochs-display driver (`src/devices/bochs_display.zig`).** Claims `pci,1234:1111` behind
    `pci-host`. Classifies the BARs by geometry (VRAM window vs the 4 KiB register page), checks the
    dispi interface id (rejecting all-ones), reads the EDID blob at offset 0, chooses the preferred
    mode when it fits VRAM, programs `XRES/YRES/BPP/VIRT_WIDTH/ENABLE` through the directly-addressed
    bochs registers, reads the mode back, maps the visible VRAM as normal non-cacheable memory
    (Device-nGnRnE would make every pixel an ordered transaction), publishes the surface, clears it
    and verifies readback. `fb mode` re-programs and re-maps at runtime.
  * **Panic-to-screen and splash.** `panic` and every fault now draw a red panic panel with the
    header, the message wrapped to the panel width, and a footer pointing at the serial console —
    before the CPU halts, with interrupts off and the other cores stopped. The boot splash is drawn as
    soon as the driver binds, before the scheduler exists. `fb test` draws a deterministic pattern for
    a screendump to be checked against.

**A phase-32 bug found by this phase.** The PCI bus never set the command register's memory-space
enable bit, so no function decoded its BAR: every MMIO read returned all-ones. The old `lspci` output
looked healthy because nothing had ever read a BAR. The panel made it visible — its dispi id read
`0xFFFF` and a naive range check accepted it. `pci.enableDecoding` now sets memory space and bus
mastering per function after BAR placement, records the command word on the function, and the driver
rejects an all-ones id. This also unblocks PCI-attached virtio transports in later phases.

**Verification (QEMU 8.2.2, `bochs-display,romfile=,xres=1280,yres=800`).** EDID parses to
manufacturer `EBI` (QEMU), name `QEMU Monitor`, preferred 1280x800; the mode is programmed and read
back, the mapping covers 4000 KiB, and `fb check` reports readback `PASS`. The test-pattern screendump
was checked pixel for pixel: eight colour bars, an 8-bit grey ramp, red/green/blue channel ramps, a
64-pixel grid, one-pixel border, four corner markers naming the channel each corner tests, and the
mode label. `fb mode 1024 768` re-modes, readback still passes, and the screendump is 1024x768.
`fb crash` produces the panic screen on the panel with the same message the serial console prints. A
boot without the device logs `no framebuffer installed` and still passes the boot self-tests. All 130
host tests pass. Screenshots are in `docs/screenshots/`.

**Limits.** One pixel format family in practice (`x8r8g8b8`; `r8g8b8`/`r5g6b5` exist in the core but
no driver uses them yet), no double buffering, dirty rectangles or compositor (phase 54), no
virtio-GPU or HDMI/CEA extension parsing, no DDC/I2C EDID fetch for a panel that does not expose a
blob, no runtime panel hotplug beyond driver unbind/rebind, and the bitmap font is a placeholder for
the vector font engine (phase 53). Big-endian scanout is detected and refused rather than drawn with
swapped channels.

### Phase 38 — Input subsystem `[x]`
**Goal:** Keys, touch, scanner.
**Build:** Event queue, virtio-keyboard, USB HID boot keyboard, absolute-pointer touch,
barcode-scanner HID fast path with prefix/suffix parsing, key remapping.
**Done when:** A scanned barcode reaches the POS app as one atomic event in < 20 ms.

**Shipped.** Input is one subsystem with one ordering contract, and every source feeds it: a
hardware keyboard, a touch panel and a barcode scanner are all the same thing to the POS app,
which sees typed characters, pointer positions and one atomic scan event in the order they
happened.

  * **Key tables (`src/lib/keymap.zig`).** The full evdev code map used by the drivers (letters,
    digits, punctuation, keypad, navigation, function keys, modifiers), the HID usage-id to
    evdev translation that phase 39's USB stack will reuse, modifier state with the desktop
    rule that shift and caps cancel for letters but not digits, and a 32-entry remap table so a
    terminal can turn a damaged or remapped key into the one the layout expects (`keymap map`,
    `keymap reset`, hit counters).
  * **Scanner state machine (`src/lib/scanner.zig`).** Hold-and-decide: a digit burst is held
    until it is unambiguous, then emitted as one `barcode` with its payload intact. Every rule
    is configurable — charset (digits or alphanumeric), prefix, suffix, minimum and maximum
    length, inter-key gap (40 ms) and whole-scan window (500 ms). A burst that breaks a rule is
    *released* keystroke by keystroke, in order, so a cashier typing a quantity or a command
    never loses characters. Prefixed scans match and swallow the prefix without leaking it into
    the payload. Statistics cover scans, releases, short scans, timeouts and overflows.
  * **Event core (`src/kernel/input.zig`).** One IRQ-safe ring of 256 ordered events with
    monotonically increasing sequence numbers and a drop-oldest policy that counts what it
    dropped, a 16-event recent ring for diagnostics, a device registry (name, kind, absolute
    range, IRQ, per-device counters), a separate console mirror for line editing, and a barcode
    notice queue so the shell can announce a scan without stealing it from the POS queue.
    `waitPop` blocks a thread on the queue; `describe` renders any event for the shell.
  * **USB HID decoders (`src/lib/input_hid.zig`).** Boot-keyboard reports are diffed against
    the previous report, so a held key produces one press and a release only when it disappears,
    rollover (usage 0x01) is ignored rather than invented, and both keys in a two-key report are
    reported. Boot mouse (signed motion, buttons, wheel) and an absolute pointer/touch report are
    decoded too. The USB host stack is phase 39; the report format and the translation are not
    waiting for it.
  * **virtio-input (`src/devices/virtio_input.zig`, `src/devices/virtio_mmio.zig`).** The first
    two-queue device in the tree: queue 0 for events, queue 1 for LED/feedback. Sixteen 64-byte
    buffers are posted and re-posted from the interrupt handler, so the device always has room;
    a polled fallback covers a device without an interrupt property. The device is classified
    from its own config space (`EV_BITS`, `ABS_INFO`): a keyboard, a relative pointer or an
    absolute tablet, with the tablet's 0..32767 axes scaled to the actual panel resolution
    (1280x800 here). SYN_REPORT commits a pointer position, buttons map to the three POS buttons,
    and wheel motion becomes scroll events. The transport is now explicitly modern:
    QEMU defaults virtio-mmio to legacy, so both run steps pass
    `-global virtio-mmio.force-legacy=false`.
  * **Shell.** `input` shows the queue, device list, scanner configuration and the last events;
    `input dump <n>` drains events; `input scan <payload>` self-tests a scan with the latency
    budget; `input viz [s]` is a live panel view with a crosshair (screenshot below);
    `input prefix/suffix/minlen/gap/charset/reset` configure the scanner; `hid` runs the HID
    decoders through the same queue. The console merges UART and keyboard characters, and a scan
    prints an asynchronous `[scan]` line.

**Evidence.** 162 host tests pass (32 of them added here). QEMU 8.2.2 with
`virtio-keyboard-device` and `virtio-tablet-device`: both bind on virtio-mmio at IRQ 78/79,
config space classifies them as `tablet` (abs 0..32767 on both axes) and `keyboard`, 72 key
events arrive from `sendkey`, and QMP absolute input produces 11 tablet events including
`pointer 351,146`, `button 1 down`, `pointer 702,292 buttons 0x01`, `button 1 up`. A scripted
13-digit scan arrives as **one** barcode event in the queue (`input dump` shows
`barcode '4006381333931' 13 chars`); the 269 ms figure is the HMP key-send window, while the
kernel measures **0 ms** from the committing suffix key to the queued event (budget 20 ms).
The HID self-test passes, `keymap map 30 31` is recorded and reset, and a boot without any input
device reports none and keeps the self-tests green. Screenshot:
`docs/screenshots/phase38-input-monitor.png`.

**Limits.** The USB host controller is phase 39: the HID decoders are tested through the kernel
queue, not through xHCI enumeration. The status queue is set up and idle; LEDs and force feedback
are not written yet. Touch is single-contact. Scanners use one configured prefix and suffix.

throughput is bounded by that loop and the 256-entry event ring. There are no isochronous
transfers, streams, suspend/resume or power management. No SuperSpeed device was exercised
(QEMU's devices are high/full speed), and there is no transaction translator for a low/full-speed
device behind a high-speed hub. The device table holds 8 slots and 16 devices; control buffers
are limited to the 4 KiB scratch page. CDC-ACM is host-tested but not exercised against a real
CDC-ACM peripheral; the FTDI bridge is the real serial proof.

### Phase 40 — Watchdog and power `[x]`
**Goal:** Recover from hangs; behave on power loss.
**Build:** Hardware watchdog kick from the scheduler, brown-out detection hooks, thermal
throttling, graceful shutdown path that flushes the journal.
**Done when:** A forced kernel hang resets the terminal and boots to a consistent state.

**Shipped.** Power is a coordinator with four independently testable pieces: a real PCI
watchdog, a scheduler heartbeat, a persistent event journal, and a thermal policy that changes
what the scheduler does. The host-testable math and record format live in `src/lib/power.zig`;
the devices and I/O live in the kernel.

  * **i6300ESB watchdog (`src/devices/i6300esb.zig`, `src/devices/builtin.zig`).** The phase-32
    PCI registry publishes QEMU's Intel 6300ESB function (`8086:25ab`) as a `wdt` driver. The driver
    maps BAR0 as Device memory, programs the two-stage timer through PCI config 0x60/0x68 using
    the direct ECAM byte/word accesses the part requires, preloads both stages for 2 s (4 s total),
    kicks the reload register from the scheduler, reads the previous-reset flag before clearing it,
    and disarms before a planned shutdown. A locked/nowayout configuration is reported, not hidden.
  * **Scheduler heartbeat (`src/kernel/sched.zig`, `src/kernel/percpu.zig`).** The tick on core 0
    kicks the watchdog every 250 ms. If the scheduler stops, the kicks stop with it; other cores
    continuing to tick cannot keep the machine alive. `power hang` sets one atomic flag that
    suppresses every heartbeat and then disables this core's interrupts, so the reset is caused by
    the hardware timer rather than a software path. The next boot reads the watchdog's reset flag
    and records why the previous session ended.
  * **Power coordinator (`src/kernel/power.zig`).** Boot history, brown-out hooks, storage
    flushers, journal boot/selftest records, `flushNow`, clean shutdown, reboot, forced hang and
    the degraded-hardware self-test. Shutdown runs the same flush path as `power flush`: every
    registered filesystem syncs, the journal gets its final record, the block device flushes, and
    only then does PSCI power off. A brown-out ISR only publishes an atomic flag; the shell's
    `power.service()` performs the emergency flush and shutdown in normal context.
  * **Persistent journal (`src/kernel/journal.zig`).** `POWER.JNL` on FAT32 partition 1 is an
    append-only power event log, not a filesystem journal (CASSAFS's write-ahead journal is phase
    43). Records are fixed 72-byte little-endian entries with a magic, version, sequence, uptime,
    wall clock, temperature, throttle and CRC32; decoding stops at the first torn or foreign
    record. A 96-record ring evicts the oldest entry, whole-file flush rewrites the file and asks
    the device to flush, and the journal reads it back. The file survives the machine reset, and
    a manual `power flush` is recorded as a power event rather than a clean shutdown.
  * **Thermal policy (`src/kernel/thermal.zig`, `src/lib/power.zig`).** A zone starts at 42 C on
    the explicitly labelled virtual sensor; a board can register a real sensor without changing
    the policy. The ladder is normal/warm/hot/critical at 70/82/92 C with 67/79/89 C hysteresis,
    mapping to 0/25/50/75% idle ticks. On a throttled tick the scheduler runs the core's idle
    thread, whose `wfi` is the actual thermal relief; the counters count injected idle ticks, not
    intentions. `thermal set`, `clear`, `selftest` and `bench` expose the policy.
  * **Shell and degraded boot.** `power [info|journal|flush|brownout|poweroff|reboot|selftest|viz|hang]`,
    `thermal [info|set|clear|selftest|bench]`, `watchdog [info|kick|selftest]`, a top-level
    `poweroff`, and `power viz` (live panel dashboard). The boot path works with no watchdog and
    no disk: the watchdog is reported absent, the journal is memory-only, `power selftest` reports
    both as `OK (degraded)`, and `power hang` is refused because there is no hardware to recover it.
    `reboot` and `poweroff` route through the coordinator so the flush and disarm paths cannot
    drift from the tested shutdown path.

**Evidence.** `zig build` clean; **197 host tests pass**, up from 187 (+10 tests in
`src/lib/power.zig`). `tools/qemu_power_test.py` runs six QEMU 8.2.2 scenarios and passes:

  * **Forced hang.** With a real `i6300esb` and a 65 MiB FAT32 disk, the harness writes
    `WATCHDOG.TXT`, flushes, then runs `power hang`. The machine resets in the 4 s window, boots
    again, and reports `previous boot was a watchdog reset` and an unclean journal; the journal
    contains `watchdog_boot`, the file is readable and `fat check` is consistent.
  * **Graceful shutdown.** `power poweroff` flushes, disarms, exits QEMU with status 0, and the
    next boot reports a clean shutdown with the file intact; `power selftest` passes on the real
    watchdog and FAT-backed journal.
  * **Brown-out.** `power brownout` runs one board hook, flushes and powers off with status 0;
    the next boot is clean and the journal records the brownout, with the file intact.
  * **Thermal.** A normal benchmark took **2212 ms**; at `thermal set 96000` the same workload
    took **3604 ms** (1.63x slower) at critical/75%, with **12,990 injected idle ticks**, and
    `thermal clear` restored 42.000 C. The host tests cover the ladder boundaries, hysteresis and
    exact duty-cycle pattern.
  * **Degraded boot.** No watchdog and no disk: both are reported as absent/memory-only,
    `power selftest` is PASS with two `OK (degraded)` lines, and `power hang` is refused.

The phase-38 input harness and phase-39 USB harness both still pass. Representative boot lines:
`i6300ESB at BAR 0x11001000: 2000 ms preload 0x7f3, two-stage reset, 4000 total`, `power PSCI off/reset ready, watchdog armed, journal FAT32 partition 1`, and after a hang `previous boot ended
in a hardware watchdog reset`.

**Limits.** The watchdog driver is specific to the i6300ESB programming model; another board's
watchdog needs its own driver behind the same coordinator. Only core 0 kicks it, so a hang confined
to another core that leaves core 0 scheduling is not detected by the watchdog (the scheduler's own
stall/accounting paths still apply). There is no NMI, stack dump or crash record before a watchdog
reset; the reset is the recovery, not a diagnosis. `POWER.JNL` is a single FAT32 file on partition
1, rewritten whole, with a 96-record ring and a 24-byte detail field; it is not CASSAFS, has no
redundant copy or atomic rename, and a manual flush is deliberately not a clean-shutdown record.
Thermal control is duty-cycle idle injection, not DVFS; QEMU has only the virtual sensor, and the
thresholds, four-step ladder and 4-tick granularity are compile-time policy. Brown-out detection is
a hook/API (`signalBrownout`) with no PMIC/ADC driver yet, and its shutdown is serviced by the shell
loop, so a shell blocked in a long command delays the emergency flush. Poweroff/reboot depend on
PSCI; `halt` with an armed watchdog still resets after the timeout, which is the phase-5 explicit
halt policy. There is no suspend, hibernate or RTC wake.

## Stage E — Storage and filesystems

### Phase 41 — CASSAFS format `[x]`
**Goal:** A crash-safe filesystem designed for till workloads.
**Build:** Log-structured design, CRC32C on every record, A/B superblocks, inode tree,
extent allocation, free-space map, on-disk versioning.
**Done when:** The format is documented and a reference dump/verify tool exists (in Zig).

**Shipped.** CASSAFS v1 is a real, byte-level format with one implementation shared by the
kernel and a host reference tool. The contract is documented in
[`docs/cassafs-format.md`](docs/cassafs-format.md); the pure codec, formatter, scanner and
reader live in `src/lib/cassafs.zig`, the partition/block adapter and shell surface in
`src/kernel/cassafs.zig`, and the read-only host verifier in `tools/cassafs.zig`.

  * **Log-structured layout.** 4096-byte blocks; A/B superblocks at blocks 0 and 1; an
    append-only log from block 2. A record is a 64-byte header block followed by
    `ceil(payload_len / 4096)` payload blocks. Each record is one of inode, data, free-space
    map or checkpoint, and records are sequence-numbered from 1 with no gaps.
  * **CRC32C everywhere.** The Castagnoli implementation covers the first 60 bytes of every
    record header and exactly `payload_len` bytes of every payload. The superblock has its own
    CRC over bytes 0..507. A torn header, a flipped payload byte, a damaged bitmap or a
    mismatched checkpoint is a typed `BadCrc`/`BadFreeMap`/`BadCheckpoint` failure before any
    metadata is trusted.
  * **A/B superblocks.** A is generation 1 and B is generation 2 after format. The scanner
    decodes both independently and selects the highest valid generation. Damaging B is a
    verified fallback to A, reported by name rather than silently hidden.
  * **Inode tree and extents.** A 268-byte inode carries kind, name, parent, size, data CRC,
    mode and up to eight 24-byte extents. Every non-root inode must have a directory parent and
    a unique name; the scanner walks each node to the root, rejects cycles, parent/non-directory
    links and duplicate siblings. Extents are ordered, contiguous in logical space and must lie
    inside a data record; the scanner computes each file's CRC from its extents and compares it
    with the inode. `cassafs cat` reads through the extents, not a side buffer.
  * **Free-space map and checkpoint.** The penultimate record is a bitmap over every volume
    block; the last is a 120-byte checkpoint naming the root inode, log head, counts and the
    free-map record. The scanner proves the bitmap marks exactly `[0, log_head)` used, proves
    the checkpoint's pointers and counters, and only then exposes the report.
  * **On-disk versioning.** Format version 1, independent record version, compatible and
    incompatible feature words, and a UUID. An unknown incompatible feature is refused rather
    than guessed; a different format version is refused at the superblock.
  * **Kernel surface.** `cassafs info|format [empty|demo]|demo|dump|verify|cat <path>|viz <s>`
    through the phase-12 shell. `format demo` builds the tree `root -> catalog -> products.db`
    and `root -> receipts -> WELCOME.TXT`; `verify` checks every record, tree edge, extent,
    data CRC and free-map bit; `dump` prints the log table, tree and extents; `viz` is the live
    dashboard. The command is registered with the driver/storage shell surface and does not
    depend on the FAT32 cache.
  * **Reference tool.** `zig build` also produces `zig-out/bin/cassafs`, which reads an image
    through `--partition N` (MBR entry) or `--offset BYTES`, uses the same library and prints
    `info`, `verify`, `dump` or `cat`. It is read-only by construction, so a QEMU image can be
    checked from outside the guest.
  * **Absence and safety.** With no disk, `cassafs info`/`verify` report
    `no block device; attach a disk with partition 1`, the kernel still passes `selftest`, and
    no write path is entered. Formatting refuses while the phase-40 FAT power journal is mounted
    on partition 1, because rewriting that volume would invalidate `POWER.JNL`; phase 43
    integrates the journal with CASSAFS.
  * **Stack-budget repair.** The full scan path measured a 46 KiB frame in the debug kernel.
    The shell's 32 KiB stack therefore wrote through its base into the adjacent watchdog
    thread's saved frame on the first full `cassafs info`, which the scheduler correctly caught
    as a corrupt frame. The fix is at the thread layer: kernel thread stacks are now 64 KiB
    (`src/kernel/thread.zig`), not a CASSAFS workaround. The failure and the repair are recorded
    here because they were a real phase-41 integration bug.

**Evidence.** `zig build` clean; **208 host tests pass**, up from 197 (+11 in
`src/lib/cassafs.zig`: CRC32C reference, superblock round trip/refusal, record header CRC,
inode codec, formatter tree/free map/checkpoint/A+B, A/B fallback, payload corruption, free-map
bit corruption, malformed fixture, path/read refusal, unknown incompatible feature). The new
`tools/qemu_cassafs_test.py` runs five scripted scenarios (eight QEMU boots) and passes:

  * **Format and read-back.** A 64 MiB partition-1 MBR disk reports no valid superblock, then

    158 data bytes**, leaving **16,364 free** blocks. `info` reads A generation 1, B generation

**Limits.** Phase 41 is the **format and reference read/verify path**. At the time it shipped
there was no mounted filesystem; phase 42 now adds the mount/VFS read path. Phase 41 still has
no write path, journal replay or garbage collection (phase 43); formatting rewrites the volume. The reference bounds are 128 inodes, 128
records, 8 extents per inode, 16 KiB per data record and 1 GiB per volume; they are compile-time
constants chosen to keep the kernel's memory bounded. A/B redundancy covers superblock damage
only; there is no redundant checkpoint, so a damaged checkpoint is reported and refused until
phase 43. The kernel adapter formats and reads **partition 1** (MBR or GPT from the existing
partition parser); it does not format the whole disk or another partition. The power journal is
still FAT-backed on partition 1, and CASSAFS formatting refuses while that journal is mounted;
CASSAFS's own journal is phase 43. There is no encryption, checksum-at-rest beyond CRC32C, or
metadata replication.

### Phase 42 — Mount and read path `[x]`
**Goal:** Read files safely through a real VFS, with mount, lookup, directory iteration and
extent reads.
**Build:** A backend-neutral VFS (node table, mount table, path normalisation, handles, read-only
access checks, stable directory iteration), a CASSAFS backend adapter, validate-before-mount,
unmount/remount, sequential and ranged reads, and honest kernel-side failure checks.

The phase-41 `cassafs info/format/verify/cat` path is unchanged.

### Phase 43 — Write path and recovery `[x]`
**Goal:** Make CASSAFS writable through the mounted VFS without weakening the phase-42
validation, and prove the bytes survive a clean shutdown, remount and soft reboot.
**Build:** File create and offset write/extend, append-only allocation from the log head into
the free map, inode supersession, chunk CRCs, new free map/checkpoint, A/B superblock generation
and readback, VFS write handles, host write tests and a real QEMU write-path harness.

**Shipped.** CASSAFS now has an append-only write path. `cassafs.createFile` allocates
`checkpoint.next_ino`, validates the parent and sibling name, appends a new inode record and
commits a new free map, checkpoint and both superblocks. `cassafs.writeFile` reads the old chunks,
rebuilds only the 16 KiB chunks touched by an offset write (zero-filling a gap past EOF), reuses
untouched extents, computes the final CRC32C, appends new data and inode records, then commits
the same way. A commit starts from `report.log_head`/`last_seq`, writes the new free map marking
the whole committed prefix used, writes the checkpoint, flushes, writes both superblocks with
`generation = max(A,B)+1`, and reads both superblocks back. The caller then rescans the complete
medium with the unchanged CRC/tree/extent/bitmap validator before updating the mounted report.
The VFS gained writable backend callbacks, `create` open flags, `writeAt`/`write`, stat refresh
from the backend, and `NoSpace`/`Exists`/`IsDirectory`/`NotFound` reasons. The shell exposes
`vfs create <path>`, `vfs write <path> <offset> <text>` and `vfs df`; `vfs selftest` now proves
write opens work and directory write opens are refused. The scanner accepts a later inode record
for the same inode number (latest copy wins, original directory slot preserved) and validates
historical free-map/checkpoint pairs while requiring the selected checkpoint's map to describe
the selected log head. Existing phase-41/42 read results remain unchanged.

only writable backend and partition 1 is the only mount.

### Phase 44 — Block and page cache `[x]`
**Goal:** Predictable performance under load.
**Build:** LRU page cache, write-back with bounded dirty pages, readahead, cache pressure
accounting.
**Done when:** Checkout commit latency stays under 100 ms while a catalog import runs.

**Shipped.** The mounted CASSAFS volume now reads and writes through a bounded 4 KiB page
cache (`src/lib/page_cache.zig`) between the VFS adapter and the partition block view. The
kernel mount owns **64 pages (256 KiB)** in `.bss`, with a **16-page (64 KiB) dirty bound**
and **four-page readahead**. Pages are evicted by LRU timestamp; a dirty victim is written
before reuse, a failed writeback keeps the page dirty and returns the error, and `flush`
writes every dirty page before flushing the block layer. The commit path calls this barrier
before and after the A/B superblock writes, so the phase-43 validity guarantees still hold.
The VFS exposes `vfs cache [stats|flush|drop|bench]`, includes cache pressure in `vfs info`
and `vfs df`, draws it in the dashboard, and `vfs selftest` now has **19 checks** including
bounded-cache and real-read-traffic proof. The on-disk format, scan, CRC/tree/extent/free-map
validation, VFS namespace and write path are unchanged.

**Evidence.**
- `zig build` is clean; `zig build test` passes **225/225**, up from 219 (+6 page-cache tests:

The format still caps a volume at 128 inodes/records, eight extents per file and 128 KiB per

cache is 64 pages / 16 dirty pages and the benchmark uses the small demo catalog, so the
latency result is evidence for this workload, not a claim about every future catalog.

### Phase 46 — VFS `[x]`
**Goal:** One interface for all storage.
**Build:** Mount points, path resolution, file operations, permissions, file locking,
inotify-style change notifications.
**Done when:** Paths resolve identically across CASSAFS, FAT32 and tmpfs.

**Shipped.** The VFS now presents three backends through one namespace: writable
CASSAFS at `/`, read-only FAT32 at `/media/usb`, and a bounded writable **tmpfs**
at `/tmp`. `src/lib/tmpfs.zig` is a 16-node, 4 KiB-per-file, zero-allocation
backend with root and nested directories, create/write/read/readdir, and chmod.
The core gained optional backend `mkdir_fn`/`chmod_fn` callbacks, permission
checks driven by on-disk mode bits, advisory whole-file shared/exclusive locks
that follow handles, and a bounded inotify-style watch/event interface
(8 watches, 16 queued events) with created/modified/mounted/unmounted events and
explicit dropped-event accounting. Handles carry their canonical path so write
events name the exact file; the VFS event ring overwrites the oldest event when a
slow consumer falls behind, never grows without bound.

The shell exposes `vfs mount tmpfs`, `vfs unmount tmpfs`, `vfs mkdir`, `vfs chmod`,
`vfs lock`, `vfs watch`, `vfs unwatch` and `vfs events`; `vfs info`/`vfs df`
report locks, watches, pending/dropped events and tmpfs usage. `vfs lock <path>`
proves exclusive refusal and shared coexistence in one booted command.

A latent input bug surfaced when the larger VFS image shifted timing: the shell
loop's `virtio_input.pollAll()` could drain a virtqueue concurrently with the
device IRQ handler. The two paths had no lock, so keyboard completions could be
freed/reposted twice and barcode digits were lost. `src/devices/virtio_input.zig`
now serialises every drain with an IRQ-safe spinlock; the unchanged input harness
again captures all 13 digits.

- `zig build` clean; `zig build test --summary all` reports **233/233**, up from

deadlock detection; they protect cooperating processes, not hostile ones.

not yet exposed as a user-space syscall; there is no unlink/rename/truncate event
because those operations are not implemented. There is one tmpfs mount, one
FAT32 mount and one CASSAFS root, and the VFS tables remain single-threaded
kernel-owned state.

### Phase 49 — Storage health `[x]`
**Goal:** Fail predictably, not suddenly.
**Build:** Bad-block handling, read-retry policy, eMMC/SD health counters, fsck, pre-failure
warnings surfaced in the supervisor UI.
**Done when:** Simulated media errors reduce to retries and warnings without data loss.

**Shipped.** The bounded policy is `src/lib/storage_health.zig`: 32 bad ranges,
a three-retry budget, healthy/degraded/failing states, media operation and sector
counters, recovered/unrecovered ledgers, one warning per transition and a scrub
that clears a quarantine but keeps the degraded history. The virtio-blk request
path (`src/devices/virtio_blk.zig`) now checks a quarantined range before
submission, rejects it with `BadBlock`, injects simulated medium errors ahead of
the device, routes real and simulated failures through the existing three-attempt
transport retry/reset path, counts a recovered request only when a retry succeeds,
and quarantines a range after the budget is exhausted. The phase-34 boot
self-test's forced timeout is deliberately excluded from health warnings, so a
clean boot is healthy rather than permanently degraded. `cassafs.fsck()` runs the
full read-only CASSAFS verifier and reports named refusals; `BadBlock` is
propagated by the CASSAFS adapter. The shell exposes `blk health`, `blk fsck`,
`blk inject read|write|flush <lba> <sectors> <failures>`, `blk clear`,
`blk scrub <lba> <sectors>` and the `blk viz` supervisor dashboard.

**Evidence.** `python3 tools/qemu_storage49_test.py` boots the real image after
re-establishing phase-45/47/48 evidence on one disk: 10,000 FAT32 rows / 220,021
B / CRC32C `0x8678e4e7`, 239 retail records, and one committed phase-48 sale with
`sales verify : PASS, 1 transaction(s)`. Baseline `blk fsck : PASS, 37 record(s),

(the CASSAFS superblock range) prints `health : degraded, warnings 1, retries 1,
recovered 1, unrecovered 0, bad blocks 0` and fsck still PASSes. A transient

`blk fsck : REFUSED: Io`; the next attempt, now quarantined, prints
`blk fsck : REFUSED: BadBlock`; health is `failing, warnings 3, retries 5,

**Limits.** QEMU virtio-blk exposes no eMMC/SD life-time or SMART registers; the

no sector remapping, ECC, automatic repair or persistent bad-block list. fsck is
read-only and does not repair; `blk scrub` only proves readability and clears a
quarantine. The read and flush paths are boot-tested; write injection shares the
same request path but is not separately exercised. The shell/block path remains
single-writer, and the harness simulates media errors rather than physically
removing the disk or cutting power mid-write.

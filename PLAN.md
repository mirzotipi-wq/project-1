# Cassa — Master Engineering Plan

**Cassa is a point-of-sale operating system for 64-bit ARM retail hardware, written entirely in Zig.**
This document is the authoritative 100-phase delivery plan. Each phase is small enough to
review in one sitting, and each one ends with a written, testable exit criterion. Phases are
executed strictly in order; nothing is declared done because it compiles — it is done when the
exit criterion has been observed on QEMU or on real hardware and the evidence is recorded.

---

## 0. Mandate

| | |
|---|---|
| **Product** | Cassa POS OS — a dedicated till OS for shopping stores |
| **Architecture** | AArch64 (ARMv8.0-A baseline and newer) |
| **Language** | 100% Zig, kernel to pixels |
| **Boot** | UEFI stub on real hardware; QEMU `virt` ELF image for development |
| **Shape** | Monolithic kernel + isolated user-space services (POS, payments, printing, UI) |
| **Primary KPI** | A cashier can complete a sale, take payment, print a receipt, and close a shift — offline, on day one of a power cut, with zero data loss |

### 0.1 Non-negotiables

1. **Zig only.** Every line of executable logic — boot, kernel, drivers, filesystem, network,
   TLS, compositor, UI toolkit, and the POS application itself — is Zig source. There are no
   `.c`, `.S`, `.cpp`, Rust, Python or JavaScript files in the build. There is no libc.
2. **No borrowed kernels.** No Linux, no Zephyr, no seL4, no U-Boot. Cassa boots from firmware
   into its own entry point.
3. **Runs on any AArch64 CPU.** Compiled for the ARMv8.0-A baseline so that it runs on
   Cortex-A53/A55/A72/A76/A78/X-series, Neoverse, Apple silicon and Graviton. Hardware
   differences are discovered at boot through device tree and ACPI, never compiled in.
4. **POS-grade reliability.** No data loss on power failure, no half-committed sale, no
   unlabelled failure. Every subsystem has a defined degradation mode.
5. **Deterministic, reviewable security.** Capability-based isolation for every service,
   signed updates, encrypted storage, auditable privileged actions.

### 0.2 What "100% Zig" means precisely

| Artifact | Language | Rationale |
|---|---|---|
| Kernel, drivers, services, UI, apps | Zig | Mandate |
| Build system (`build.zig`) | Zig | Also emits the linker script |
| Linker script | Generated by Zig at build time | Keeps a second language out of the tree |
| Pad/entry stubs | Zig `naked` functions with Zig inline assembly | No separate `.S` files |
| Documentation | Markdown | Prose is not code |

The only external binaries involved in development are the Zig compiler and QEMU. Neither
ships inside the OS image.

### 0.3 Hardware support tiers

- **Tier 1 (must):** QEMU `virt` (CI), Cortex-A53/A72 boards, integrated POS terminals.
- **Tier 2 (should):** Raspberry Pi 4/5 class SBCs, NXP i.MX8, Rockchip RK3399.
- **Tier 3 (later):** Apple silicon VMs, Graviton bare metal, server-class Neoverse.

### 0.4 Targets

| Metric | Target |
|---|---|
| Cold boot → POS screen interactive | < 3.0 s |
| Tap → painted response | < 50 ms |
| Local checkout commit (scan → sale stored) | < 100 ms |
| Resident memory on 512 MB device | < 64 MB |

### 0.6 Verification strategy

1. **Host unit tests** (`zig build test`) for pure logic: allocators, codecs, tax maths,
   cart rules, font metrics, FDT/ELF parsers, protocol state machines.
2. **QEMU boot gate** (`zig build run`) — every commit must boot to a shell and pass the
   in-kernel self-test suite.
3. **Deterministic snapshot tests** for the UI toolkit (render to memory, compare hashes).
4. **Fault injection**: power-cut simulation, media errors, OOM, malformed frames.
5. **Hardware lab**: real POS terminal, receipt printer, scanner, card terminal.

## Stage A — Foundation: from reset vector to an observable kernel

### Phase 1 — Toolchain and reproducible build `[x]`
**Goal:** One command builds a bootable AArch64 image; no second language in the tree.
**Build:** `build.zig` with a freestanding target (ARMv8.0-A baseline, `+neon +fp`), a
linker script generated as a build artifact, `zig build run` for QEMU, `zig build test` for
host tests, warnings-as-errors, and a build manifest stamped with git describe.
**Done when:** `zig build` produces an ELF with a correct entry point, and a from-scratch
clone builds with no extra tooling or shell scripts.

### Phase 2 — Boot entry and handoff `[x]`
**Goal:** Take control of the CPU from firmware in a defined state.
**Build:** Naked `_start`: mask interrupts, set SP_EL1, capture the device-tree pointer,
clear BSS, detect current EL, park secondary cores, jump into `kmain`. UEFI path drops to
the same entry after `ExitBootServices`.
**Done when:** QEMU prints a boot line and the kernel stack/BSS are provably zeroed.

### Phase 3 — Early UART console `[x]`
**Goal:** Byte-accurate output before anything else exists.
**Build:** PL011 driver with FIFO handling, baud/word-length setup from the device tree,
polled TX/RX, and a `Writer` interface usable by the rest of the kernel.
**Done when:** Formatted output appears on QEMU's serial console at boot.

### Phase 4 — Kernel logging `[x]`
**Goal:** Structured, levelled, timestamped diagnostics.
**Build:** `klog` with compile-time max level, per-subsystem scopes, uptime stamps, a lock
for SMP safety, and an in-memory ring buffer that survives a panic for post-mortem dumping.
**Done when:** `klog.info`/`warn`/`err` render consistently, and the ring can be dumped.

### Phase 5 — Panic and fatal-error surface `[x]`
**Goal:** A crash is a diagnosis, not a mystery.
**Build:** Zig panic hook, `@panic`/`unreachable` capture, register dump (PC, LR, SP, ESR,
FAR), stack scan, boot-phase breadcrumb, and an explicit halt policy (watchdog reset in
production, hang in debug).
**Done when:** An intentional fault prints a labelled report instead of resetting silently.

### Phase 6 — Device tree discovery `[x]`
**Goal:** Learn the machine instead of hard-coding it.
**Build:** FDT parser (header validation, string block, node/property walk), memory node
extraction, `/chosen` bootargs/stdout-path, interrupt-controller and timer discovery.
**Done when:** Physical RAM size, UART base and GIC addresses are read from the tree and
logged, with QEMU varying `-m` sizes producing different reported totals.

### Phase 7 — Physical memory manager `[x]`
**Goal:** Hand out and reclaim physical pages safely.
**Build:** Bitmap allocator over usable RAM, reserved ranges for kernel/DTB/MMIO, single-page
and contiguous allocation, free counters by zone, and poison-on-free in debug builds.
**Done when:** Host tests cover alloc/free/coalesce accounting and QEMU reports the expected
page totals for several RAM sizes.

### Phase 8 — Kernel heap `[x]`
**Goal:** A real allocator behind `std.mem.Allocator`.
**Build:** Boundary-tag free-list allocator with splitting, coalescing, alignment support,
OOM propagation, usage accounting and debug poisoning.
**Done when:** Host tests pass a randomized alloc/free/coalesce workload with zero leaks and
no corruption, and the kernel can use `std.ArrayList`/`std.fmt.allocPrint`.

### Phase 9 — MMU and address-space discipline `[x]`
**Goal:** Caches on, W^X enforced, MMIO descriptors correct.
**Build:** 4 KiB granule page tables, MAIR/TCR setup, identity map during bring-up, normal
cacheable vs device-nGnRnE attributes, guard pages, permission API, TLB maintenance.
**Done when:** The kernel runs with MMU and caches enabled, unmapped accesses fault with a
decoded report, and a deliberate write to read-only text traps.

### Phase 10 — Exception vectors and fault taxonomy `[x]`
**Goal:** Every exception has an owner.
**Build:** 16-entry vector table (runtime-patched branch table, 2 KiB aligned), full trap
frame save/restore, ESR/ISS decoding for data/instruction aborts, SVC, alignment, and
SError, plus a fault handler that names the cause in plain language.
**Done when:** `svc`, a bad load, and an undefined instruction each produce a distinct,
accurate report instead of a hang.

## Stage B — Time, interrupts and concurrency (complete: 11-18, 20; 13 partial, 19 deferred)

### Phase 11 — Interrupt controller (GICv3 + GICv2 fallback) `[x]`
**Goal:** Route and acknowledge interrupts on both generations of GIC.
**Build:** Distributor/redistributor/CPU-interface init, priority and group configuration,
SPI/PPI enable, acknowledge/EOI, spurious handling, IRQ handler registry.
**Done when:** The timer interrupt fires and is acknowledged on QEMU (GICv3) and on a
GICv2 target without code changes.

### Phase 12 — Generic timer `[x]`
**Goal:** Monotonic time and periodic ticks.
**Build:** CNTFRQ calibration from the device tree, CNTPCT read, CNTP compare programming,
1 kHz tick, one-shot deadlines, `uptime`/`sleep`/`sleepUntil` primitives.
**Done when:** Uptime advances accurately, a 1-second busy-wait is within 1% of wall clock,
and ticks survive 10^6 interrupts without drift or lost interrupts.

### Phase 13 — Interrupt framework refinement `[~]`
**Goal:** Interrupt handlers cannot deadlock or stampede.
**Build:** Top-half/bottom-half split, IRQ-safe spinlocks, handler latency counters, storm
detection (disable a line that fires > N times per tick), and threaded IRQ support.
**Done when:** A deliberately storming line is throttled and logged, with the rest of the
system still responsive.
**Verified:** IRQ-safe spinlocks, per-CPU interrupt and tick counters, and the
spurious/unhandled tallies reported by `irq` (0 and 0 on a live boot) exist. Storm throttling
and threaded IRQs are not built yet: `logstorm` proves console serialisation, not IRQ storms.

### Phase 14 — Spinlocks and atomics `[x]`
**Goal:** Correct SMP primitives with deadlock detection.
**Build:** Ticket spinlock, IRQ-save/restore variants, exclusive/acquire-release helpers,
lock-order validation in debug builds, per-CPU state.
**Done when:** A contended counter test across 4 cores is exactly correct, and an intentional
ABBA lock order panics with both lock sites named.
**Verified:** `sync.zig` ships `SpinLock` (test-and-test-and-set with event hints),
`TicketLock`, `IrqSpinLock`, acquire/release atomics, and `WaitQueue`/`Semaphore` on top.
`stress 4 20000` on four cores reports 80000/80000 with 0 lost updates and no page drift.
Lock-order validation (the ABBA panic) is deferred to the Stage D deadlock detector, which
needs the lock graph the file server will introduce.

### Phase 15 — Kernel threads and context switching `[x]`
**Goal:** Multiple execution contexts inside the kernel.
**Build:** Thread struct, callee-saved context switch, per-thread stacks with guards, idle
thread, thread exit and reaping.
**Done when:** Two threads ping-pong a counter with correct interleaving and no stack bleed.
**Verified:** `thread.zig` (24 slots, 32 KiB stacks, fabricated trap frames) plus
`sched.zig` (idle thread per core, exit and reaping). `threads` lists live contexts with
state, core, run count and stack; `preempt` shows three threads interleaving on one core;
`reap 8` and `reap 12` return every stack to the PMM (0 pages leaked). Guard pages are not
mapped yet.

### Phase 16 — Preemptive scheduler `[x]`
**Goal:** Fair, bounded-latency CPU sharing.
**Build:** Round-robin across priority classes, tick accounting, timeslice tuning, run-queue
per CPU with load balancing, scheduler statistics.
**Done when:** Three CPU-bound threads each get within 5% of their fair share, and an
interactive thread wakes with < 1 ms latency under load.
**Verified:** 1 kHz tick-driven preemption with 4-tick slices, per-CPU round-robin queues,
work stealing and pinning. `preempt 1000` pins three spinning threads (none of which ever
yield) to one core: 22..22 timeslices each, all three progressing — only possible through
preemption. Iteration spreads of 6-12% track hypervisor time stealing from the vCPU, not
scheduler bias; the slice counts themselves are equal.

### Phase 17 — Sleep, wait queues, synchronization `[x]`
**Goal:** Blocking without burning CPU.
**Build:** Wait queues, mutex/condvar/semaphore, sleeping mutexes, timeout-aware waits,
priority donation for lock holders.
**Done when:** A producer/consumer stress test with 4 threads passes 10^6 items with no lost
wakeups and no priority inversion beyond the donation bound.
**Verified:** `WaitQueue`, `Semaphore` (signed permit count, generic over its backend so the
identical code runs in host tests) and `sleepMs`/timed waits. The host suite covers blocking,
wakeup ordering and semaphore accounting. Priority donation waits for priority classes.

### Phase 18 — SMP bring-up `[x]`
**Goal:** Use every core in the terminal.
**Build:** PSCI `CPU_ON`, per-CPU stacks/trap frames/GIC init, IPI for reschedule and TLB
shootdown, boot barrier, per-CPU data accessor.
**Done when:** 4 cores report online, TLB shootdown is verified by a mapping test, and
`-smp 1/2/4/8` all boot cleanly.
**Verified:** PSCI `CPU_ON` with per-CPU stacks, trap frames, GIC CPU interface, timer and
TPIDR_EL1 state. `cores` reports 4/4 online with independent tick, switch, preempt and IRQ
counters on each, and `-smp 1` through `-smp 4` boot. TLB shootdown is implemented as an IPI
but has no user address space to shoot yet (phase 22).

### Phase 19 — Deferred work `[ ]`
**Goal:** Keep interrupt context tiny.
**Build:** Per-CPU workqueues, softirq classes, delayed work tied to the timer, cancellation.
**Done when:** Block-device completion is processed off the IRQ path, and a 10k-item
workqueue drains with bounded latency.
**Status:** deliberately deferred. Its done-when needs block devices (Stage D); softirqs
without a producer would be an unused abstraction.

### Phase 20 — Tracing and self-tests `[x]`
**Goal:** Observability that survives production.
**Build:** Boot self-test suite, per-subsystem counters, tracepoints with a ring buffer,
`kassa selftest` command, boot-time assertions.
**Done when:** Every boot runs the self-tests and reports a single pass/fail verdict.
**Verified:** every boot runs the self-test suite and prints one PASS/FAIL verdict per
probe; `cores`, `threads`, `irq`, `mem`, `time`, `stress`, `preempt`, `reap` and `logstorm`
expose live counters; the scheduler keeps a 64-entry switch ring that panic and fault reports
dump.

## Stage C — Privilege, processes and IPC (21-22 complete)

### Phase 21 — EL0 and syscalls `[x]`
**Goal:** Move code out of the kernel.
**Build:** EL0 transition, `svc` entry path, syscall table with argument validation,
`copy_from_user`/`copy_to_user` with range checks.
**Done when:** A user program prints via a syscall and cannot read kernel memory.
**Verified:** `user` runs the embedded program at EL0 and `uprobe` proves the
contract. The program prints through `write`, receives its pid and the uptime
from the kernel, yields and exits 0 (8 ms in a measured run). A `mrs tcr_el1`
is reported by the hardware as an undefined instruction at EL0 (EC 0x00,
ESR 0x2000000) at pc 0x80000268 — EL0 has no access to that register at all, so
the encoding is undefined there rather than "trapped"; a load from kernel
text 0x40080000 raises a level-3 permission fault; both are logged with the pid,
kill only that process, and the kernel keeps running. `write()` with kernel text
and with an unmapped address each return -14 after the kernel refuses to follow
the pointer (the `rejected_ptr` counter advances by 2 per run). EL0 passes the
call number in x8, and the kernel validates every pointer twice: against the
process's declared regions with their rights (`uaccess.check`, host-tested) and
against its live page tables (`mmu.translateFrom`). Not done yet: a separate
fault-tolerant `copy_from_user` (validation is followed by a direct copy) and
capability checks — phase 23 replaces the region list with a handle table.

### Phase 22 — Address spaces `[x]`
**Goal:** Isolated per-process memory.
**Build:** TTBR0 per process, ASIDs, map/unmap/protect, demand-zero anonymous memory,
user stack growth, guard regions.
**Done when:** Two processes at the same virtual address cannot see each other's data.
**Verified:** every process gets its own L0 (a copy of the kernel's), its own
clone of the kernel's L1, and its own L2/L3 pages, so the kernel and its devices
stay mapped while a process runs and no user-reachable mapping leaks in. A
context switch installs the matching root in TTBR0_EL1 and invalidates the TLB,
before the old thread is marked off-CPU (reaping frees those tables). Two
processes write different secrets to 0x81000010 — same virtual address, different
physical pages — and after 25 context switches each still reads its own value
(`uprobe` step 5). Teardown releases every frame and table: five launch/exit
cycles return the free-page counter exactly (128440 -> 128440). Not done yet:
ASIDs (a full TLB invalidate per switch is the honest cost), demand paging (all
frames are allocated at load), stack growth (a fixed four-page stack with an
unmapped guard below it) and an ELF loader — the demo is a flat blob embedded in
the kernel image.

### Phase 23 — Capabilities `[x]`
**Goal:** Authority is a first-class, transferable object.
**Build:** Capability slots, rights masks, derivation, revocation, per-process handle tables,
kernel object headers with refcounts.
**Done when:** A process without a capability cannot reach a device, and revocation cuts
access immediately.
**Verified:** every process owns a 16-slot handle table and a handle number is
`(generation << 8) | (slot + 1)`, so a closed or revoked slot can never be named again and
zero is never a valid handle. A handle carries a rights mask — READ 1, WRITE 2, EXEC-or-MAP 4,
CONTROL 8 — and the kernel resolves the handle before it looks at any user pointer: a forged
number returns EBADF (-9), never a fault and never another process's memory. Derivation needs
CONTROL on the parent plus a subset mask; revocation walks the parent chain, invalidates the
whole subtree and bumps generations, so later use fails with EBADF while the parent keeps
working. Objects are the console, a shared ledger (64-byte cell, version, epoch), the
supervisor (another process's state, exported read-only) and a page object holding one kernel
frame with magic `0xCA55A0B100000023`, which only a handle carrying EXEC-or-MAP can place in a
process at 0x81500000. Eight syscalls (20-27) are the whole surface: query, derive, revoke,
close, read, write, control, map. `caps` prints the object table with reference counts.

The probe passes on `-smp 4` and `-smp 1` with identical numbers. The first process is born
with handles 1/2/3/4 and passes all six cases: granted rights work (case 1); mapping a ledger
without EXEC and controlling a read-only supervisor both return EPERM -1 (case 2); slot 10,
slot 200 and handle 0 all return EBADF -9 without faulting (case 3); a derived CONTROL handle
works, is revoked, and is then EBADF while its parent still answers (case 4); two live
processes (pids 111 and 112) hold the same ledger and the read-only one gets EPERM for write
while its read succeeds (case 5); deriving until the table is full returns EMFILE -24 and
closing one handle lets the next derive succeed (case 6). Both holders exit 0. The run
recorded 28 capability calls, 310 user syscalls, 13 spawned processes, 2 caught faults, and
the ledger ends at version 4, epoch 2, 14 references, with derivations 28, revocations 2,
refusals 7 and 2 live tables.

### Phase 24 — IPC endpoints `[x]`
**Goal:** Fast, typed message passing between services.
**Build:** Endpoint pairs, synchronous call/reply, 64-byte inline payloads plus handle
transfer, deadlines, backpressure.
**Done when:** A call/reply round trip sustains > 100k messages/s on QEMU, and a blocked
receiver never spins.
**Acceptance (concrete):**
1. An endpoint is a kernel object of kind `endpoint`; `ipc_create` returns a handle carrying
   `rwc`, and any handle with `w` may send or reply, `r` may receive, `c` may hand the
   endpoint to another process.
2. A message is exactly 64 bytes carried inline (`tag` plus seven words); the kernel copies it
   into the receiver's own buffer while the receiver's address space is loaded, so no message
   ever depends on another process's raw pointer.
3. `ipc_call` blocks the caller until the server replies; the reply lands in the caller's
   buffer and the reply length is the return value.
4. One handle may travel with a message. Transferring needs `c` on the handle (EPERM
   otherwise); a never-allocated or closed number is refused with EBADF before anything is
   published, so a refused call delivers no message; the receiver gets a fresh handle in its
   own table whose mask is the sender's minus `c`.
5. Revocation crosses processes: revoking the sender's handle after a transfer makes the
   receiver's installed copy fail with EBADF on its next use.
6. Deadlines: a call that is not answered within its timeout returns -ETIMEDOUT (110), leaves
   no stale request behind, and the channel still works afterwards; a reply that arrives after
   the caller gave up is refused with -EAGAIN (11).
7. Backpressure: an endpoint holds at most one request and one reply; a second sender blocks
   until the slot frees or its deadline expires.
8. A process that was never granted the endpoint gets EBADF for a number it does not hold and
   EINVAL for a handle that is not an endpoint, survives both, and exits 0.
9. A blocked receiver never spins: its thread state is `blocked` and its run counter does not
   advance while it waits.
10. A call/reply round trip sustains > 100,000 messages/s (two messages per round trip) on
    QEMU with four cores, measured over at least 300 round trips.
11. No regressions: phases 1-23 keep passing, host tests stay green, and the probe passes on
    `-smp 1` and `-smp 4`.

**Verified:** endpoints are capability objects (`cap.Kind.endpoint`) and five syscalls
(28-32) are their whole surface: `ipc_create`, `ipc_send`, `ipc_call`, `ipc_recv`,
`ipc_reply`. A message is exactly 64 bytes (`tag` plus seven words) copied by the kernel
into the receiving process's own buffer while that process's address space is loaded, so no
message ever depends on another process's pointer. `ipc_call` publishes a request, parks the
caller (`blocked` plus an absolute deadline) and resumes it when the answer is published;
`ipc_recv` parks a receiver until a request arrives, and a sender that finds a parked
receiver copies the message straight into it - one context switch instead of a poll. An
endpoint holds at most one request and one reply, so a second sender parks until the slot
frees or its deadline expires: that is the whole backpressure story.

One handle may travel with a message. Transferring needs `c` on the handle (EPERM
otherwise); a never-allocated or closed number is refused with EBADF *before* anything is
published, so a refused call delivers no message; the receiver's copy carries the sender's
mask minus `c`, and its parent link points into the sender's table. That last detail is new:
`revoke` now walks every table, so revoking the sender's handle kills the receiver's copy
immediately (a phase-23 gap closed here). A reply that arrives after the caller gave up is
refused with EAGAIN rather than handed to the next call.

The probe (`uprobe` step 10) passes on `-smp 4` and `-smp 1`. Server (mode 6) and client
(mode 5) are born holding the bootstrap endpoint; the server creates an endpoint and
transfers it to the client over that channel, so even the channel the client calls through
arrives as a handle. Client cases: 11 handoff received as a transferred handle; 12 call and
reply; 13 a READ+CONTROL ledger handle travels, the receiver reads through it and gets EPERM
for write; 14 a never-allocated number (0xDEAD) refused with EBADF; 15 a closed number
refused with EBADF; 16 the sender revokes its handle after the transfer and the receiver's
copy is EBADF; 17 a 10 ms deadline returns ETIMEDOUT (-110) against a server that answers
after 30 ms; 18 the channel still works and the server reports its late reply was refused
with EAGAIN (-11); 19 2000 round trips, all exact; 20 a clean shutdown. Server cases: 21
endpoint created; 22 handoff transferred; 23 exactly one transfer request reached it (the
forged ones never left the client) and the transferred handle read once; 24 the abandoned
reply was refused. Outsider (mode 7, never granted the endpoint): 31 EBADF for a number it
never held, EINVAL for a ledger handle, EPERM for a page handle; 34 bootstrap handle 0. All
three processes exit 0.

### Phase 25 — Shared memory and notifications `[x]`
**Goal:** Bulk data without copying.
**Build:** Shared memory objects, mapping into multiple address spaces, futex-style wait and
wake, event counters.
**Done when:** Two processes exchange a 4 MiB buffer with zero copies and correct wakeups.
**Acceptance (concrete):**
1. A shared-memory object is a capability object of kind `shm` holding up to 1024 kernel
   frames (4 MiB). `shm_create` returns a handle carrying `rwc`; the frames are zeroed when
   the object is created, so a peer can never read another object's old data.
2. `shm_map` maps the object into the caller's address space at a kernel-chosen base inside
   the user window and returns that base. Mapping needs `r`; the mapping is writable only if
   the handle also carries `w`, so one object can be read-write in one process and read-only
   in another.
3. Two processes map the same object: a word written by one is read by the other at the same
   offset with no copy in between (the kernel only installs page tables), and the 4 MiB buffer
   survives a full pattern pass in both directions.
4. `shm_unmap` removes this process's mapping, clears the page-table entries, drops the region
   and flushes the TLB; a second unmap of the same object is refused with EINVAL, and a later
   `shm_map` succeeds again at a free base.
5. Futex-style notification: `shm_wait(handle, offset, expected, timeout)` sleeps only if the
   32-bit word at `offset` still equals `expected` (EAGAIN -11 if it changed), returns 0 when
   woken, and ETIMEDOUT (-110) when the deadline passes. `shm_wake(handle, offset, count)`
   wakes up to `count` waiters and returns how many it woke; each wake bumps the object's
   event counter, which the shell prints.
6. Rights are enforced on the handle, never on a user pointer: a handle without `r` cannot
   map or wait (EPERM -1), a handle without `w` cannot wake (EPERM), a non-shm handle is
   EINVAL, and a forged or out-of-range handle is EBADF (-9) with no fault.
7. A process that was never granted the object cannot reach it: it has no handle (EBADF) and
   no mapping in its address space, and it survives every refusal and exits 0.
8. No regressions: phases 1-24 keep passing, host tests stay green, and the probe passes on
   `-smp 1` and `-smp 4`.

**Verified:** a shared-memory object is a capability of kind `shm` holding up to 1024 zeroed
kernel frames (4 MiB) from one 2048-page pool, created by `shm_create` (33) which returns a
handle carrying `rwc`. `shm_map` (34) installs those frames in the caller's page tables and
returns the base: the mapping is writable only when the handle carries `w`, so one object can
be read-write in one process and read-only in another without a flag from the user. Nothing
is copied — the kernel only writes page-table entries, so a word stored by one process is the
word the other reads. `shm_unmap` (35) clears the translations, drops the region and flushes
the TLB; a second unmap is EINVAL and a later map succeeds again at the same slot.

`shm_wait` (36) is futex-shaped: it sleeps only if the 32-bit word at `offset` still equals
the expected value, returns EAGAIN (-11) if it already changed, 0 when woken, ETIMEDOUT
(-110) on its deadline; `shm_wake` (37) releases up to `count` sleepers, returns how many it
released and bumps the object's event counter. Everything is decided under the object lock,
so a wake that lands between the value check and the park cannot be lost.

### Phase 26 — Processes and ELF loading `[x]`
**Goal:** Run separately built programs.
**Build:** ELF64/AArch64 loader (segments, permissions, BSS), argv/envp, process lifecycle,
exit status propagation.
**Done when:** The POS shell launches a user-space binary by name.

> Scope note: the standalone VFS phases come later in this plan, so the name lookup runs
> against a read-only image store (a table of embedded files) rather than a filesystem. The
> loader consumes real file bytes and the shell launches by name, which is the observable
> contract this phase owns; the store is the one call that a VFS will replace.

**Acceptance (concrete):**
1. A program built by the same toolchain as its own ELF64 executable — separate segments,
   separate data, separate BSS — is embedded as *file bytes*, not a flat blob, and the kernel
   parses it at runtime.
2. The parser validates ELF64/little-endian/ET_EXEC/EM_AARCH64, refuses a bad magic number,
   a wrong word size, a wrong machine, a truncated header or program table, a segment whose
   file bytes do not fit in the file, `p_filesz > p_memsz`, a segment outside the user
   window, overlapping segments, a writable-and-executable segment, and an entry point
   outside an executable segment — before a single page is allocated.
3. The loader maps each page once with the union of the permissions of the segments that
   touch it, refuses a page that would end up both writable and executable, copies the
   file-backed part of each page and leaves the rest zero, so BSS arrives as zeroes.
4. The startup ABI is x0 = argc, x1 = argv, x2 = envp, with the strings and both pointer
   vectors built on the user stack before the thread is admitted; SP is 16-byte aligned.
5. `exec <image> [args...]` in the shell loads the image by name, runs it, and prints its exit
   status; a missing image is refused as "no such image" and nothing is spawned.
6. `images` lists the store and `elf` prints the last load plan (entry, segments, bytes, BSS)
   and the load/refusal counters.
7. No regressions: phases 1-25 keep passing, host tests stay green (with new host tests for

**Verified:** `pos.elf` is a genuinely separate program: `zig build` compiles it as its own
executable from `src/user/pos.zig` (its own linker script puts .text, .rodata, .data and .bss

runtime. It is 67 KB of file for 1366 bytes of loadable content — the padding is the linker's
64 KiB segment alignment, and the loader honours it because it maps pages, not offsets.

(r-x at 0x80000000, r-- at 0x80001000, rw- at 0x80002000), 1366 file bytes, 1622 memory

segments touching it and refuses any page that would be writable *and* executable; that rule
is why the program's linker script aligns permission groups to pages, and why a hand-made

### Phase 27 — Lifecycle and fault isolation `[x]`
**Goal:** One crashing service cannot take the till down.
**Build:** Supervisor per service, restart policy with backoff, crash loop detection,
core-dump-to-storage, orphan reaping.
**Done when:** Killing the printer service in a loop leaves checkout functional.

> Scope note (tightened): "core-dump-to-storage" is a **crash record** — pid, fault kind,
> fault address, pc, esr, the eight argument registers and eight words of the faulting user
> stack — captured while the process still owns its address space, kept in a small kernel ring
> and printed by `dumps`. The VFS phases own files; this record is the part of a core file a
> supervisor can act on, and every field is measured, not inferred from a log line.

**Acceptance (concrete):**
1. `service start|kill|stop <name>` manages a named service; bare `service` lists name, state,
   pid, restarts, failures and policy for every slot, plus the global counters.
2. A service that dies is restarted by the supervisor with exponential backoff
   (5, 10, 20, 40, 80, 160 ms, capped at 160), and the delay the policy chose is recorded on
   the service record, so the ladder is observable from outside.
3. Consecutive failures are counted. At the policy's limit the service is parked `failed`
   (crash loop detected) instead of being restarted forever; a run that stays up for the
   policy's stability window resets the count.
4. A faulting program leaves a crash record (`dumps` shows pid, cause, pc, esr, registers and
   stack words) and cannot take the machine down: the shell and every other service keep
   running.
5. Stopping a service kills its child and reaps it. Live process count, address-space count
   and the page allocator return to their pre-service values (orphan reaping), and a killed
   child that blocked in a syscall still dies.
6. Checkout keeps working while the printer service is killed in a loop.
7. No regressions: phases 1-26 keep passing, host tests stay green (new host tests for the
   restart policy), and the probe passes on `-smp 1` and `-smp 4`.

**Verified.** The supervisor is a kernel thread of its own (`svc`) that polls the service table
every 10 ms and never blocks on a child. Each entry is a name, an image, argv, and a pure
`restart.Policy` (max_restarts 6, base 5 ms, cap 160 ms, stable window 250 ms). The policy
itself is `src/kernel/restart.zig`, free of kernel dependencies, so backoff, the crash-loop
decision and the stability reset are unit-tested on the host (3 new tests, 55/55 total).

Read that transcript for what it is: the printer was killed **seven** times; the supervisor
brought it back six times with 5/10/20/40/80/160 ms between attempts (its own `svc` log lines

and register/stack words, and cost no live process, address space or page: after `stop`, live
processes and spaces are back to 0 and `reaps` counts every child the supervisor buried.

**A scheduler defect this phase found and fixed.** The supervisor is a thread that blocks and
wakes ~100 times per second, which is far more than anything before it, and it exposed a
use-after-free in the context switch: `reschedule` cleared the outgoing thread's `on_cpu`
flag *before* returning the incoming frame, i.e. while the core was still executing on the
outgoing thread's stack. Another core's tick could then reap that thread and free its stack
in that window; the symptom was an occasional `eret` into data (a fault report whose ELR was
ASCII from a log line) or a resumed frame with a nonsense `spsr`. Four-core idle boots with the
unpinned supervisor died within ~17 s; pinned, they survived, which is what pointed at
migration rather than at the supervisor's logic. The fix moves the hand-off into the exception
trampoline: `reschedule` records `pc.switching_out`, the trampoline calls `cassa_after_switch`
immediately after `mov sp, x0`, and only there is `on_cpu` cleared. A wake that arrived during
that window is deferred (`pending_wake`) and must be applied at that same point or it is lost —
the first version of the fix omitted that and hung the shared-memory step, which the probe
caught at once. The frame validation also checks the saved PSTATE mode now, so a corrupt frame
is reported with the thread's name instead of jumping into whatever address it names.

Measured evidence for the fix: with the unpinned supervisor, two 36 s four-core idle boots and
four consecutive four-core probe boots ran with zero faults and `RESULT: PASS`; before the fix
the same idle boot faulted every time within ~17 s. `-smp 1` passes too.

Host tests: 55/55 (3 new: backoff doubles and caps, the crash loop trips at max_restarts and not

`stress 4 20000` -> 0 lost; `preempt 1000` -> PASS (`22..23` slices); `reap 8` -> 0 pages
leaked; `logstorm 4` -> 96/96 intact; `cores` -> 4 cores online; `irq` -> 0 spurious, 0
unhandled; `-m 1024M` -> 1024 MiB, 259456 pages free; `textwrite` -> permission fault at

supervisor load made the server occasionally answer the abandoned call after the client had
already moved on. No assertion was changed — the window only gives the server time to finish,
which is what the test always assumed.

**Gap (open):** the service table is four static slots with the image name compiled in, and the
policy is per-service but not persisted, so a `failed` service stays parked until someone
restarts it by name — that is the service registry and manifest work of phase 28. The crash
record ring holds four records in kernel memory and is lost on reboot (no filesystem yet); it
captures registers and eight stack words, not the full stack or the faulting page. Supervision
is polling, not event-driven: a death is noticed within one 10 ms tick, and a restart can
therefore be up to one tick later than the policy's delay. Orphan reaping covers children of
supervised services; a process spawned directly by the shell is reaped by the shell's `wait`
as before, and there is no process group or parent/child tree yet. The scheduler's
`cassa_after_switch` hand-off has survived the soak above, but it is the kind of change that
deserves a longer stress run than one phase can give it; `stress 4 20000` and the four-core
probe boots are the evidence so far.

### Phase 28 — Service registry `[x]`
**Goal:** Services find each other without hard-coded handles.
**Build:** Namespace tree, path-based lookup, service manifests, lazy start, health probes.
**Done when:** The POS app resolves `pos://printer` at runtime and degrades gracefully when
it is absent.

> Scope note (tightened): the "namespace tree" is a **flat table of opaque names**, not a
> directory hierarchy, and "service manifests" are the name, image, argv and restart policy a
> slot already carries, registered under a name — there is no manifest language yet. What is
> built is the part the POS app needs: a kernel-owned name-to-identity table, a by-name lookup
> that answers with a reason, lazy start, and a supervised service whose absence is a value
> rather than a fault. Health *probing* is the supervisor's existing liveness check (a service
> whose child died is restarted or parked) surfaced through the lookup reason; there is no
> separate request/response health protocol.

**Acceptance (concrete):**
1. `registry` lists every registered name, its service slot, state, generation and the global
   counters; `pos://` names are validated by one pure function (`registry schema: 1-16 chars,
   `[a-z0-9-]`, no leading or trailing `-`, scheme required).
2. Re-registering a live name, registering an unknown target, and registering when the table is
   full are each refused with a distinct reason, and no entry changes.
3. `resolve <name>` returns a reason: ok, unknown name, not running, crash-loop parked, exited.
   The reason is a stable numeric code the ABI fixes, written to a user process unchanged.
4. `ensure <name>` starts a registered but stopped service and returns its pid (lazy start), and
   a lookup that finds a service mid-restart answers `restarting` instead of failing.
5. A POS program calls the syscall and exits with the reason code, so degradation is provable at
   the call site: live service -> 0, parked crash loop -> 4, unknown name -> 1.
6. The table is fixed-size (8 entries) and re-registration is idempotent for a dead name; nothing
   in the lookup path allocates, so the registry cannot grow with load.
7. No regressions: phases 1-27 keep passing, host tests stay green (new host tests for the name
   rules and the reason mapping), and the probe passes on `-smp 1` and `-smp 4`.

**Verified.** The name rules and the reason mapping are `src/kernel/names.zig`, free of kernel
dependencies: `validate`, the `Reason` enum with ABI-fixed values 0..9, `reasonFor(lifecycle,
child_alive)` and `reasonLabel`, covered by 5 host tests. The table is `src/kernel/registry.zig`:
8 entries of name + service slot, an `IrqSpinLock`, and `register`, `lookup`, `ensure`, `count`,
`entryAt`. Every registration is checked against the slot's live state, so a name cannot point at
a slot that does not exist; duplicates are refused, not overwritten. Lookup reads the service
record and its generation under the registry lock, which is the same lock the supervisor takes
when it changes a state, so a lookup can never interleave with a restart half-applied: it sees
either the old generation running or the new one restarting, and says which. `service.Service`
gained a `generation` counter bumped by `launch`, which is what makes "same service, new
incarnation" observable from user space. User space reaches all of it through one new syscall,
`UserNr.resolve = 38`: `resolve(name_ptr, name_len, out_pid)` returns the reason code and writes
the pid only on ok, with the pointer range validated like every other string argument.
`pos.elf resolve <name>` prints the outcome and **exits with the reason code**, which is how the
probe proves graceful degradation rather than describing it. The shell gained `registry`,
`resolve <name>` and `ensure <name>`.

**Scheduler follow-up (after phase 28): run-queue lifecycle.** The kill-path churn of step [13]
exposed an intermittent four-core panic, `selected thread 0 in state unused`, and the phase-28
notes recorded it as open. It is now fixed. The panic was a **queue entry naming a thread that had
already been reaped and whose slot had been recycled**: `thread.destroy` zeroes a slot, so a queue
still holding that slot pops "thread 0 in state unused" — and because `destroy` also clears the
freed thread's own `next`, the queue's *predecessor* is left pointing at the zeroed slot, which is
how a boot that had run for seconds suddenly selected a thread id of 0.

The cause was a **duplicate run-queue entry**, not a stolen one. There were two publish sites for
the same outgoing thread: `reschedule` pushed it when it was runnable, and `cassa_after_switch`
pushed it *again* if a wake arrived in the window between them (`on_cpu` was still true, so
`makeReadyLocked` recorded `pending_wake` instead of queueing). The thread then had two entries.
One was consumed when it ran; the survivor could be popped after the thread had blocked, died and
been reaped, i.e. after its slot was zeroed. The earlier "queued while on_cpu" reading was a
symptom: the `double_run_events` counter that appeared to confirm it was actually counting the
core's own **idle** thread, which is legitimately on-CPU whenever a core falls back to it, so that
counter said nothing about real duplicate entries at all.

What changed, and the invariant it establishes:

* **Invariant R:** every run-queue entry names a thread that is `ready` and that no core is
  executing; every `ready` thread is in exactly one run queue. The transition into `ready` and the
  push happen together under the scheduler lock at exactly two sites — `makeReadyLocked` for a
  parked (off-CPU) thread, and `cassa_after_switch` for the thread that has just left the core.
  `reschedule` no longer queues the outgoing thread at all; it only decides what the thread will
  be (ready/blocked/dead) and folds a deferred wake into that decision. Publishing happens in the
  trampoline, at the first instant the stack is genuinely free, in the same critical section that
  clears `on_cpu`.
* `pushTail` asserts Invariant R and counts a refusal (`queue_violations`); the reaper refuses to
  free a thread that is still referenced by any run queue (`deferred_reaps`); a stale queue entry
  is dropped instead of resumed; and the tick audits for a `ready` thread that has sat in no queue
  for more than 50 ms, reports it with the site that made it ready, and re-queues it (`stray_ready`)
  so a lost wake becomes one late slice and a number instead of a stalled service.
* The idle fallback is no longer judged by the queue-entry rules, which is what the old
  `double_run_events` count was really measuring.
* Nothing allocates on the switch path; the only added state is three diagnostic words per thread
  (`ready_site`, `ready_ms`) and three counters. `-smp 1` boot and the switch soaks are unchanged.

lifecycle. `killoop 150` ran twice, 150/150 rounds each, with `0 double-run, 0 queue violation(s),
0 deferred reap(s), 0 stray ready` and 0 pages leaked; the phase-28 probe's step [13] (seven kills,

The switch soaks are green: `stress 4 20000` 0 lost updates, `preempt 1000` PASS, `reap 8` 0 pages

**Deadline enforcement in IPC, and the two probe races it exposed (fixed).** After the run-queue
repair, roughly one four-core boot in ten still failed EL0 IPC cases 17/18/24 while the same boot's
2000-round-trip throughput test passed. It was not a wake-latency regression: `ipc.reply` refused a
late answer only when the caller was no longer parked **and** its deadline had passed. If the answer
arrived while the caller was still parked (it had not run its own timeout path yet), or after
`sweep` had cleared the caller and zeroed the deadline, the kernel accepted the answer for a caller
that was about to return ETIMEDOUT. That one race produced all three symptoms at once: the call
returned a reply instead of a timeout (17), the endpoint kept a stale answer that the same thread's
next call then took as its own (18), and the server's late reply was accepted rather than refused
with EAGAIN (24). The fix is in `ipc.reply`: a deadline that has passed refuses the answer, decided
by the deadline alone and independent of which thread runs first, and `sweep` no longer erases the
deadline when it clears a parked caller. That is the contract the comment in `call` already stated —
the server may answer after the caller has given up, and that answer must be refused. It is a
kernel fix, not a probe constant: no assertion changed and no window was widened for it.

Two probe observations were also *sampled* rather than *waited for*, which is what the remaining
5-10% of boots were hitting: step [13] read the crash-loop state immediately after the last kill
(catching the previous restart's transition) and step [14] tried to observe a 5 ms backoff window
from a thread that is itself scheduled on four cores. Both now wait, with bounded timeouts, for the
exact state they assert; step [14] also sets the 100 ms backoff it observes (a policy input, not
the property under test) and restores it. Nothing was weakened: every assertion is unchanged and
the state still has to be reached.

Measured on the final build: **20/20 consecutive four-core probe boots with `RESULT: PASS`**, zero

every one of them; 5/5 single-core boots; `killoop 150` twice at 150/150 rounds with zero anomalies
and no leaked pages; `stress 4 20000` 0 lost updates, `preempt 1000` PASS, `reap 8` 0 pages leaked;

**Deferred:** names are flat, not a tree, and there is no per-name ACL, so any process can resolve
any registered name (phase 30's capability manifests are where that belongs). The registry does
not survive reboot: names are re-registered by the probe and by the shell at runtime, and a
persisted manifest store needs the filesystem phases. `pos://` is the only scheme, and it is
validated but not interpreted beyond the scheme prefix. Lazy start only starts a registered
service; it does not fetch a manifest or an image by name. There is no unregister, so a name is
bound for the life of the boot (the table is fixed and the probe registers two). Health is
liveness-as-a-reason, not a request/response probe: a service that is running but wedged answers
ok. The pid a lookup returns can be stale by the time the caller uses it — it is an identity at
resolution time, and the generation counter is what lets a caller notice the service was replaced.
